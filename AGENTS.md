# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- Adding an i18n message domain takes FOUR registrations, not one: `src/lib/i18n/messages/index.ts` (en and fr spreads) plus the domain lists in `src/lib/i18n/messages.test.ts` and `src/lib/i18n/unusedKeys.test.ts`; keys built via template literals also need a `DYNAMIC_PREFIXES` entry in the latter. `noEmDashes.test.ts` bans em/en dashes across all user-facing copy.
- Improvisation/chord-scale product decisions (why reference not drill, why no modes curriculum) live in `.planning/design/improvisation.md`; the engine is `src/lib/theory/chordScale.ts`, read by FOUR surfaces (the Lookup board, the comping loop's SCALE overlay via `compBarScale`, `/learn`'s chord-tones-vs-scale-tones concept lesson `ChordScaleConcept.svelte`, and `/practice`'s chord-scale drill `chordScaleQuestion.ts` via `improvGuideFor`/`verdictForLetter`) so none of them can ever name the same scale differently.
- Prettier is NOT a project dependency and there is no config: running `npx prettier --write` reformats whole files (spaces, double quotes) against the repo's tab + single-quote style. Match the surrounding file by hand instead.
- One control idiom app-wide: a mono uppercase field label over a row of `Button` chips, `variant="primary"` (vermilion) for the selected one. Canonical example `CompingLoop.svelte` (FORME / TON / TEMPO); hand-rolling bordered button rows instead is what made the voicing drill look foreign. Show hierarchy between two control groups with a `border-top: 2px` rule and placement, not with a second button style.
- The four interval colours are fixed, but flagging is still possible: vermilion is the app's standing attention accent (retry lines, active lesson rail, careful notes) and dashed outlines mean "borrowed". `--color-faint` is decorative only and must never carry text or a marker anyone is asked to read (app.css says so; an 8px faint keyboard marker shipped once and was invisible). The improvisation board's visual grammar is specified in `.planning/design/improvisation.md` section 5.5.
- All sound goes through the single engine `src/lib/audio/audio.ts` (lazy Tone import, sampler-first, no-throw, sound toggle). Key-tap sound is already centralised inside `PianoKeyboard.svelte`, so a component that mounts a keyboard must not also play the tapped note. Any playback that outlives its click (comp loop, chord demo) carries a generation token so a second start cancels the first. ONE deliberate exception: `src/lib/audio/strudel.ts` wraps `@strudel/web` (pinned in package.json, self-hosted, never a CDN) for the comping loop's live-code escape hatch, because a live-coded pattern needs its own scheduler that audio.ts's Tone Transport cannot express; the two engines never sound at once (`CompingLoop.svelte` stops one before starting the other). Only synthesized waveforms ever ship in a seeded pattern (never a sample name), so it stays offline-honest the same way the rest of audio.ts does.
- The live-code escape hatch's editor (`StrudelEditor.svelte`) and pianoroll (`src/lib/audio/strudelPianoroll.ts`) are BOTH lazy: neither's chunk (CodeMirror, `@strudel/draw`) loads until the panel is opened, mirroring `strudel.ts`'s own lazy-on-first-use discipline - a static top-level import of `StrudelEditor.svelte` silently defeats this (verified once by grepping the built page chunk for CodeMirror source and finding it eagerly bundled; fixed by gating the import behind `toggleLiveCode()` and rendering through `{#await}`). Use only `@codemirror/state` + `@codemirror/view` + `@codemirror/lang-javascript` + `@codemirror/language` (+ `@lezer/highlight` for tag-based styling), never `@strudel/codemirror` - that package also highlights but drags in vim/emacs keymaps, autocomplete, and 40+ themes this app never uses. For the pianoroll, don't call `Pattern.prototype.pianoroll()`/`.draw()` directly: it silently creates a hidden full-viewport canvas via `getDrawContext()` (even from its own `cleanupDraw()` teardown helper) and its animation-frame bookkeeping has no reliable external stop. Instead wrap the lower-level `Drawer` + `drawPianoroll` exports (`@strudel/draw`) with your own owned canvas and a plain `{ now, pattern }` scheduler shim - see `strudelPianoroll.ts`'s header for the full reasoning. `@strudel/draw@1.2.6` is pinned to match the `@strudel/core@1.2.6` that `@strudel/web@1.3.0` already pulls in transitively (no duplicate core).
- CodeMirror 6 mounts and responds to real DOM events fine under Vitest's jsdom environment (no polyfill needed) - verified directly, so editor components get real component tests rather than a mocked stand-in. Its editable surface is `.cm-content` (not a `<textarea>`), so a test reads it via `.textContent` and edits it by mutating `.textContent` then firing a native `input` event (CodeMirror's own DOM observer picks up the diff) rather than `fireEvent.input(el, { target: { value } })`. A multi-line document renders one `.cm-line` block element per line with no `\n` in between, so join `.querySelectorAll('.cm-line')` with `'\n'` rather than reading `.textContent` on the container directly. jsdom's `HTMLCanvasElement.getContext('2d')` returns null (no native `canvas` package installed), so any canvas-consuming component test must stub `HTMLCanvasElement.prototype.getContext` itself.
- The drill-seed channels (`src/lib/practice/drillSeeds.ts`) are the user ASKING for a chord, and they are one-shot: `/practice`'s `load()` drains them before composing, so anything the round drops is destroyed, not deferred. Seeds therefore lead the queue and are held OUT of the daily-target slice (`sliceRound` cuts only the composed half); the round's question budget is widened by two questions per seed (the seed plus its delayed retry), so a missed request is re-asked in the round that honoured it. Every writer across the two channels hands off to `mode: 'see-play'`, because every one of them has just shown the user the answer: the drill channel (Lookup "Drill it", the end card's "Fix this one", Progress's danger cards, weak list and per-symbol buttons) and the lesson channel (`InteractiveLesson.svelte`'s `setLessonSeeds`). Both channels are drained on every mount, so `buildSeededItems` CONCATENATES them (lesson seeds first, then drill seeds, deduped by `factId`) rather than picking a winner - honouring one and discarding the other destroys the loser's chord. Composed dedup against a seed also keys on `factId`, never the item id, precisely because the seed asks a different mode of the same fact; a card dropped by that dedup is still due unless the seed asks that exact card (same fact AND same mode), so only the others are counted into `waiting`.
- Song play-through (Phase 40) is a THIRD, wholly separate one-shot channel, `src/lib/practice/songPlaythrough.ts`, never routed through `buildSeededItems`: it keeps repeats and sheet order (the milestone's explicit exception to the usual dedupe-by-factId rule) and `load()` branches to it FIRST, before any FSRS due-loading or `composePracticeQueue` call, with `roundTarget = Infinity` - so a play-through is never diluted by the pool and never sliced by the daily target, unlike the other two channels which still widen/lead a shared, bounded round. `songProvenance.ts`'s `resolveDrillableSymbol` normalizes a song's chord to the nearest catalog chord-formula fact (enharmonic root or quality alias) or reports it unresolvable, so an exotic symbol (9, 13, add9, sus2...) is counted as skipped rather than crashing the run. A parallel one-shot channel, `src/lib/practice/compSongSeed.ts`, feeds the same song's chords into the comping loop's `barsFromSymbols` (compLoop.ts, `buildCompBars`'s song-driven sibling, `roman` always `''`) for "Play over it" on `/learn` - a completely different, ungraded surface, never merged with the practice-side channels.
- A queue item's `card` snapshot goes stale the moment ANY same-identity item elsewhere in the same queue gets graded: `recordGrade` computes its FSRS transition off whatever `CardRecord` object it is handed, and Dexie's `put()` is last-write-wins keyed on `(factId, mode)`. `/practice`'s `completeCarded` refreshes every queue item sharing that identity on every grade (not just the one just answered) for exactly this reason - a song play-through repeat is the reachable case today, but the same hazard would hit any future feature that puts one card at two queue positions.
- The common-tone bridge step (`ProgressionDrill.svelte`, between bar N's play and bar N+1's name) is ungraded/unscheduled, same as the existing function-reveal - no FSRS fact type for a chordA-to-chordB pair exists and none should be invented for it. `guideToneMotion`/`toGuideToneBar` (`guideTones.ts`) are generic over any two `ProgressionBar`s across all 12 keys and 3 templates (not just the fixed C-major lesson demo); `fallingSemitones` is always computed, never assumed 1, because the minor ii-V-i's V-to-i motion is a whole step. The bridge's harder "play" answer target (`bridgePlayTarget`) is literally the outgoing bar's own shell (held 3rd + falling 7th), matchChord-graded.
- A synthetic `/practice` item spends the bounded round's DAILY_TARGET question budget but never writes an FSRS grade, so every synthetic family's per-round draw MUST be capped small (the host's SYNTHETIC_*_COUNT consts; voicing's cap is practiceQueue's `SYNTHETIC_VOICING_COUNT` + `sampleVoicingItems`, applied at the host AFTER the review-maturity and song filters). Voicing shipped uncapped once (one item per due seventh chord) and starved the scheduler for months - same chords daily, due backlog pinned over the intro gate, no new material; the full mechanism lives in `sampleVoicingItems`' docstring and the throughput regression is pinned in `practiceQueue.test.ts`.
- Adding a synthetic (non-persisted) `/practice` family (voicing/progression/inversion/chord-scale precedent) means updating the `vi.mock('$lib/practice/practiceQueue', ...)` stub block in EVERY route/e2e test that renders `/practice` and expects a fixed due-count (`grep -rl "syntheticVoicingItems: () => \[\]"` finds them, ~12 files as of chord-scale): each one stubs the OTHER synthetic builders to `[]`/fixed values to keep its due-count assertions exact, and a new builder left unstubbed silently inflates those counts (caught as "5 CARDS DUE TODAY" instead of "3", not a compile error).
- tonal quirk (verified against tonal 6.4.3): `Chord.get(...).type` - `spellChord`'s `quality` field - is the empty string for some real, correctly-spelled qualities (e.g. `add9` AND the catalog's own `7#5`), not just unrecognized input. `songProvenance.normalizeSymbolForMatch`'s `${rootChroma}:${quality}` identity therefore collides across unrelated chords whenever quality is empty; `resolveDrillableSymbol` refuses to resolve through an empty-quality key rather than risk a wrong remap.
