# Phase 34 — UI Design Contract

> Visual and interaction contract for the earn-the-symbol progression drill's escalating hint
> ladder (SCAF-01) and beginner keyboard span (SCAF-02). Generated by gsd-ui-researcher from
> LOCKED design docs (sketch 024-A + `counting-hint-grammar.md` §024), autonomous mode (user
> away). Every decision below is either directly locked by 34-CONTEXT.md, directly precedented
> by shipped code (Phase 32 `CountingChipRow`, Phase 33 `ShellVoicingDrill` self-contained
> maturity read, Phase 25 `.ghost` hatch), or an explicit default chosen under 34-CONTEXT's
> "Claude's Discretion" grant. No `AskUserQuestion` was used.

## Copywriting Contract

All new copy lives in the existing `progressions.*` i18n domain (`src/lib/i18n/messages/progressions.ts`), following that file's own documented rule: chord symbols, roman numerals, and note letters are NEVER routed through `t()` (Symbol Immunity); only surrounding words are keyed. No em dashes anywhere (periods/colons/middots only, per project-wide rule).

| Element | Copy (FR, primary) | Copy (EN) |
|---------|------|------|
| Reveal control, depth 0 (LOCKED exact copy, 34-CONTEXT) | "Afficher un indice ▾" | "Show a hint ▾" |
| Reveal control, depth 1→2 (next: quality+count) | "Montrer la qualité et le compte" | "Show the quality and count" |
| Reveal control, depth 2→3 (next: ghost keys) | "Montre-moi" | "Show me" |
| Rung 1 tag | "INDICE {n} · LE DEGRÉ" | "HINT {n} · THE DEGREE" |
| Rung 1 body | "Le {roman} se construit sur la {ordinal} note de {key} {mode}. Fondamentale : {root}." | "The {roman} is built on the {ordinal} note of {key} {mode}. Root: {root}." |
| Rung 2 tag | "INDICE {n} · LA QUALITÉ ET LE COMPTE" | "HINT {n} · THE QUALITY AND COUNT" |
| Rung 2 body (precedes `CountingChipRow`) | "Sur le {roman}, l'accord est {qualityWord}. Empile en comptant :" | "On the {roman}, the chord is {qualityWord}. Stack it by counting:" |
| Rung 3 tag | "INDICE {n} · MONTRE-MOI" | "HINT {n} · SHOW ME" |
| Rung 3 body | "Les touches en pointillé indiquent où jouer. Joue-les, puis vérifie." | "The dashed keys show where to play. Play them, then check." |
| Closing note (ladder exhausted, symbol still hidden) | "Le symbole reste caché. Tu le gagnes toujours." | "The symbol stays hidden. You still earn it." |
| Beginner-keyboard caption (shown only at 1-octave span) | "Clavier réduit à une octave (niveau débutant)." | "Keyboard reduced to one octave (beginner level)." |
| Empty state | not applicable — this phase has no list/empty-collection surface | — |
| Error state | not applicable — wrong-answer copy is pre-existing (`progressions.retry.wrongPlay`, byte-unchanged per REG-01); the hint ladder itself never "errors" | — |
| Destructive confirmation | not applicable — no destructive action in this phase | — |

**Quality word (`qualityWord` above, one of four values used by the drill's existing templates):** reuse the app's existing quality-description helpers (`mnemonicFor`/`familyLineFor` from `$lib/copy/mnemonics`, already imported by `HintLadder.svelte` for the exact same purpose) rather than hand-authoring a fifth source of quality copy. If those helpers don't already phrase a given quality (`m7`, `7`, `maj7`, `m7b5`) in a way that fits this sentence shape, fall back to the literal FR words: mineur 7 (`m7`), de dominante (`7`), majeur 7 (`maj7`), demi-diminué (`m7b5`).

**Ordinal (`{ordinal}` above):** French ordinal words for scale degrees 1-7 (1ʳᵉ, 2ᵉ, 3ᵉ, 4ᵉ, 5ᵉ, 6ᵉ, 7ᵉ) — a small local map inside `ProgressionDrill.svelte`, since no existing helper produces this and it is trivial (7 entries, no `tonal`/theory computation needed).

**French fit rule (013):** if any of the above overflows its container at phone width (390px), abbreviate per the existing 013 precedent (e.g. shorten "Montrer la qualité et le compte" → "Montrer qualité + compte" or similar) — exact abbreviated form left to the executor, provided the meaning and the escalating-hint framing survive.

## Component Contract (phase-specific — beyond the generic template)

This phase's actual design risk is component-level, not generic-dimension-level. The sections
below are the load-bearing part of this UI-SPEC.

### 1. Hint ladder — new component, NOT an extension of `HintLadder.svelte`

**Decision (resolves 34-CONTEXT's "Claude's Discretion" item):** build the ladder as markup
**inline inside `ProgressionDrill.svelte`** (not a new standalone `.svelte` file, and NOT a
mode/layer grafted onto the existing shared `HintLadder.svelte`).

Rationale:
- The existing `HintLadder.svelte` is a shared component already consumed by `RecallSession.svelte`
  and `WhyTheseNotes.svelte`, with an API (`symbol` + fixed `'family'|'formula'|'keyboard'|'spelling'`
  layer kinds) that does not fit this drill's actual rungs (degree→root instructional text,
  `CountingChipRow`, ghost keys on the LIVE play keyboard). Grafting a 5th layer kind onto it
  would touch a shared component outside this phase's scope and risk regressing Recall/BuildSession
  (REG-01 binding explicitly scopes this phase to `ProgressionDrill.svelte`).
- `CountingChipRow.svelte` remains the single source of truth for the count rung either way —
  it is imported directly, not re-authored.

**Interaction contract (mirrors `HintLadder.svelte`'s proven escalating-cumulative pattern, so the
app's hint-ladder INTERACTION language stays one grammar even though the component is separate):**
- One reveal control, cumulative reveal: each tap adds the next rung; already-revealed rungs stay
  visible (never collapse).
- Depth 0 → shows only the reveal control, labelled "Afficher un indice ▾".
- Rendered ONLY during `step === 'play'` (the step that was hard-blocked in the original bug —
  `step === 'name'` is already unblockable via its existing multiple-choice chips and needs no ladder).
- Rung reveal depth resets to 0 whenever the cursor (current bar) changes — i.e. wrap the ladder's
  local depth state (or the whole block) so a fresh bar starts the ladder closed again. Depth does
  **NOT** reset on a wrong Check/`playRetry` within the same bar (a wrong guess must not punish by
  hiding hints already earned).
- The chord symbol (`ChordGlyph`, the raw `bar.symbol` string) must NEVER appear inside any rung,
  at any depth. Only: the roman numeral (already always-visible, unchanged), the root note letter,
  role-shorthand markers (R/3/5/7), and `CountingChipRow`'s tone/gap chips.
- Style: reuse `Button variant="ghost"` with the exact same dashed-quiet-control override
  `HintLadder.svelte` already applies (`border-style: dashed; border-color: var(--color-faint);
  color: var(--color-muted)`, solidifying to ink on hover/focus) — do not invent a new "quiet
  control" visual.
- Reuse the `stamp-in` 240ms keyframe (`.stamp` class, already in `app.css`) on each newly-revealed
  rung, matching `HintLadder.svelte`'s own reveal animation.
- `data-testid` convention: prefix with `progression-` to keep this instance unambiguous from the
  shared `HintLadder.svelte` in test queries — `progression-hint-ladder`, `progression-hint-cta`,
  `progression-hint-layer` (with `data-layer="degree" | "count" | "ghost"`), `progression-hint-closing-line`.

### 2. Rung content (3 rungs max, richest last — locked 010-A pattern)

| Rung (`data-layer`) | Content | Notes |
|---|---|---|
| `degree` | Roman numeral → scale degree ordinal → root note letter (see Copywriting Contract) | Derive the ordinal from the bar's roman numeral via a small local `ROMAN_TO_DEGREE` map inside `ProgressionDrill.svelte` (e.g. `{ i:1, ii:2, iiø:2, iii:3, IV:4, iv:4, V:5, vi:6, VII:7, vii:7 }` extended to the app's actual template vocabulary) — do NOT add a `degree` field to `ProgressionBar`/`progressions.ts`; this keeps the change scoped to `ProgressionDrill.svelte` only, per REG-01's literal scope note. The root letter itself is already available via `spellChord(currentBar.symbol).root` (no new derivation). |
| `count` | `<CountingChipRow chord={spellChord(currentBar.symbol)} />` (imported directly, `showLegend` left at its component default of `true`) preceded by the one-line intro sentence | This is the ONE place this rung's content comes from — no parallel chip markup is hand-rolled |
| `ghost` | Instructional line only; the actual ghost-hatched keys render on the drill's own live `PianoKeyboard` (see §3), not inside the rung text block | The rung's own `<div class="rung">` still renders (for the stacked-receipt visual + tag), but its "content" is the keyboard reacting, not new markup inside the rung |

Tier tags renumber sequentially from whichever rungs are actually offered at the current maturity
(see §4) — mirrors `HintLadder.svelte`'s own `tierLabel`/renumbering precedent exactly (a card at
`subtract` stage sees "Indice 1 · la qualité…" / "Indice 2 · montre-moi", never "Indice 2" / "Indice 3").

### 3. Ghost keys on the live keyboard (rung `ghost`, once revealed)

- Populate `PianoKeyboard`'s existing `ghostKeys` prop (shipped in Phase 25, `pianoKeyboardGhost.test.ts`)
  with one entry per chord tone: `{ letter, octave: <the keyboard's base octave>, marker }` where
  `marker` is the role shorthand `R` / `3` / `5` / `7` (root/third/fifth/seventh) — mirrors
  `shellVoicing.ts`'s existing `optionalMarkers` R/5 marker vocabulary, extended to all four roles.
- `ghostKeys` is empty/undefined until the `ghost` rung is revealed; it must never populate before
  that tap (no always-on ghost hint — the 024-C anti-pattern explicitly rejected).
- This is purely additive to the existing `<PianoKeyboard notes={[]} interactive {selected}
  onToggle={toggleKey} />` call in the play step — `notes` stays `[]` (unanswered), `ghostKeys` is
  the only new prop passed, so the existing interactive/selection wiring is untouched.
- Because `notes` is `[]` while unanswered, no interval-role fill ever competes with the ghost
  class (`PianoKeyboard`'s existing rule: a role always wins over ghost) — no new precedence logic
  needed.

### 4. Maturity signal driving both the ladder fade (SCAF-01) and the keyboard span (SCAF-02)

**Decision:** reuse `shellVoicing.ts`'s existing `voicingStageForChord(cards)` function and its
exact `State.New` / `State.Learning` / `State.Review` thresholds (Phase 33's precedent), computed
per the CURRENT bar's own chord symbol — not a new maturity metric, not a progression-level signal.

Read pattern: mirror `ShellVoicingDrill.svelte`'s own self-contained pattern exactly — call
`getAllCards()` from `$lib/srs/deck` directly inside `ProgressionDrill.svelte` (same async
guarded-against-staleness load already proven there), filter to the current bar's symbol, and pass
the result through `voicingStageForChord`. This keeps the maturity read entirely inside
`ProgressionDrill.svelte` (no host/`practiceQueue.ts` changes needed — `ProgressionQueueItem` has
no card/stage field today and does not need one), so the standalone `/progressions` route and the
Practice-hub-embedded instance behave identically with zero host wiring.

| Stage (per current bar's symbol) | Ladder rungs offered | Keyboard span |
|---|---|---|
| `meet` (no cards yet, or all `State.New`) | All 3: `degree`, `count`, `ghost` | 1 octave (beginner) |
| `subtract` (past New, not yet Review) | 2: `count`, `ghost` (the `degree` rung is dropped — some exposure has already happened) | 1 octave (beginner) |
| `drill` (any card has reached `State.Review`) | 0 — **no hint ladder rendered at all** (a mature card offers none, per the locked fading-scaffold rule) | 2 octaves (full span) |

Pass the resulting octave count explicitly to `PianoKeyboard`'s existing `octaves` prop
(`octaves={stage === 'drill' ? 2 : 1}`) rather than leaving it on auto width-measurement — SCAF-02
requires the 1-octave reduction to hold regardless of viewport width at beginner level, which the
component's existing self-measure fallback does not guarantee on its own.

**Tonic-anchoring interpretation (flagged for the planner):** the sketch mockup shows the
1-octave keyboard's white keys literally relabeled starting at the progression's tonic (e.g.
Si♭-Do-Ré-Mi♭-Fa-Sol-La-Si♭ for a B♭-major progression). `PianoKeyboard`'s underlying letter
layout is always C-anchored (`WHITE_LETTER_PATTERN` in `keyboardLayout.ts` never varies by key) —
introducing tonic-relabeling would be a genuinely new keyboard-layout mechanism, which 34-CONTEXT's
discretion note explicitly says to avoid ("reusing existing keyboard-span infra… rather than a new
mechanism"). **Default: do not relabel the keyboard's letters.** Keep `PianoKeyboard` exactly as
today (C-anchored), only toggling its `octaves` count. The existing `assignNotesToKeys` wrap-around
fallback (already shipped, chroma-based, used for exotic spellings) still resolves every chord tone
to a visible key within the 1-octave span even when the tonic isn't C, so the practical goal ("fewer
keys, every needed note still reachable") is satisfied without new layout logic — this is a
deliberate scope reduction from the sketch's literal mockup, not an oversight. If the executor finds
this reads as visually confusing in practice (e.g. a B♭ tonic's keys wrapping oddly), flag it back
rather than inventing a tonic-rotation feature mid-implementation.

### 5. Beginner-keyboard caption

When the keyboard is rendering at 1 octave (`meet`/`subtract` stages), show the small caption
"Clavier réduit à une octave (niveau débutant)." near the Step 2 register line (mirrors the
sketch's own inline note). Use the existing muted/faint label styling (`--color-muted`,
`--text-label`) — no new visual treatment. Omit the caption entirely at 2-octave span (`drill`
stage) — it would be noise once the keyboard is already at full size.
