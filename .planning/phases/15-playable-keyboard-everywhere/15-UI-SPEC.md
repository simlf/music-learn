# Phase 15 — UI Design Contract

> Visual and interaction contract for Playable Keyboard Everywhere. Generated by gsd-ui-researcher from ROADMAP.md's Phase 15 entry, REQUIREMENTS.md (KBD-01/02/03), sketch 008 (`.planning/sketches/008-keyboard-everywhere/`, winner Variant A: docked bottom bar), and the existing Print Shop identity + `PianoKeyboard.svelte` contract (locked since Phase 1, extended through Phases 3/9/12). No CONTEXT.md or RESEARCH.md exists for this phase; every open call below is resolved inline and marked **AUTONOMOUS DECISION** so the checker and planner never have to re-litigate it.

## Scope Decisions (autonomous — resolved without CONTEXT.md)

These are the judgment calls the roadmap/requirements left open. Each is resolved and justified so the checker and planner never have to re-derive them.

1. **The docked keyboard is the SAME keyboard each page already renders, relocated — never a second, duplicate keyboard.** Every one of the five KBD-01 pages already renders a `PianoKeyboard` (or, on Scales, an equivalent hand-rolled keyboard) inline, in whichever mode that moment needs (`interactive`, `inspectable`, `constructable`, or ScaleKeyboardDrill's own tap-to-progress keys). Phase 15's job is to take that existing element out of normal document flow and pin it to the viewport bottom in a shared chrome, not to add a redundant always-visible second keyboard alongside it. This is the only reading consistent with sketch 008's own mock (a single keyboard docked below one scrolling Recall card, not two) and with the "content cost" argument that won 008 over 008-B (which explicitly risked "one keyboard per surface, potentially several").
2. **Theory gains a NEW playable keyboard it did not have before.** `/theory` today only shows display-only (`ChordExample`) keyboards with no tap/sound affordance at all. KBD-01 explicitly lists `/theory` as in-scope, so this phase adds one always-present, always-inspectable (tap-to-hear, non-scoring) docked keyboard to that page — the only page where this phase is a pure addition rather than a relocation.
3. **Mode precedence inside the dock is exactly today's per-page mode logic, unchanged.** The docked keyboard is `interactive` (Drills construction, Recall Mode A) or `constructable` (Recall Mode C / BuildSession) only while that surface's question is actively awaiting an answer; it falls back to `inspectable` (tap-to-hear + inspect, no scoring, no selection state) the instant there is no live question to answer (reveal states, Recall Mode B multiple-choice, Lookup, Theory, between-question gaps). This single rule is what makes KBD-03 true by construction: there is never a moment where two input surfaces exist for the same fact, so "free exploration" and "the active answer" are always mutually exclusive states of the one docked element, never two competing widgets.
4. **`/build` and `/songs` and `/progress` are explicitly OUT of scope.** ROADMAP's Phase 15 goal and KBD-01's requirement text both name exactly five pages (Lookup, `/drills`, `/recall`, `/scales`, `/theory`). `/build`'s standalone flow already has its own working `constructable` keyboard inline and is not named; it keeps its current in-flow (non-docked) presentation unchanged. Widening scope to `/build` would touch BuildSession's standalone completion-screen layout for no requirement-driven reason.
5. **No sound toggle control is added to the dock.** Sketch 008 Variant A/B both mocked a per-keyboard `SOUND ON/OFF` chip, but the real app already has exactly one sound toggle, on `/progress` (`Button` with `aria-label="Toggle sound"`, wired to `setSoundEnabled`/`soundEnabled`). KBD-01 only requires the docked keyboard to *honor* the persisted toggle (`soundEnabled()` gating every `playNote`/`playChord` call, already the audio engine's existing contract) — adding a second, redundant toggle inside the dock would fork the one-source-of-truth control the app already has. The dock has no sound-state chrome at all.
6. **Scales' own keyboard (not `PianoKeyboard`) still docks, but only its key-strip — the degree/direction register stays in scrolling content.** `ScaleKeyboardDrill.svelte` renders its own keys (documented reason: `PianoKeyboard`'s `assignNotesToKeys` can collapse scale-degree placements it needs distinct). Mirroring how Recall's card content (chord glyph, note chips, grade row) stays in the scrolling page while only the keyboard element itself docks, Scales' "DEGREE {n} OF 8 · {direction}" register line and any legend stay in the scrolling page; only the tappable key rows move into the dock.
7. **Short-landscape phones (existing `max-height: 600px and (orientation: landscape)` Drills two-pane, Phase 9-03) suppress the new fixed dock chrome and keep today's two-pane layout as-is.** That layout already clears `main`'s `min-height` and places the keyboard in its own always-visible pane — stacking a second fixed bottom bar on top of an already height-constrained, already-cleared layout would eat vertical space twice for no benefit, since the keyboard pane there is already effectively "docked" (always on screen, no scroll needed to reach it). This is the one page-family where the dock chrome intentionally does not apply; the keyboard's mode-precedence rule (Decision 3) still applies unchanged within that pane.
8. **Default state: expanded, on every fresh device.** Matches KBD-02's "thumb-reachable" promise as the default experience and sketch 008's own default-open mock. The collapse choice persists per-device via `localStorage` (`music-learn:docked-keyboard-collapsed`, boolean, following the established `music-learn:*` key convention), read once at mount, defaulting to expanded (`false`) when absent or unreadable — same defensive-read/fallback shape as every other `music-learn:*` flag in the codebase (e.g. `audio.ts`'s `readStoredEnabled`).

## Dock Chrome Contract

**Positioning:** `position: fixed; left: 0; right: 0; bottom: 0; z-index` above all page content (no existing fixed-position chrome exists in the app today — the masthead is static, not sticky — so this is the app's first fixed element and needs no z-index conflict resolution).

**Structure (top to bottom):**
1. **Handle bar** — solid `--color-ink` fill, `--color-paper-bright` text, `text-label font-mono uppercase` styling, centered label, minimum 44px height (touch target), full width, `cursor: pointer`, tap toggles collapsed/expanded. A visual grip mark (small horizontal bar, `--color-paper-bright` on `--color-ink`) sits beside the label, matching sketch 008's `.grip` treatment — purely decorative, `aria-hidden`.
2. **Keyboard surface** (hidden when collapsed) — `--color-paper-bright` background, 2px `--color-ink` top border separating it from the handle, hosts the current page's `PianoKeyboard` (or Scales' key-strip) at its existing fixed 160px height, unchanged responsive 1-octave/2-octave logic (`octavesForWidth`) — the dock does not override or fix the octave count.
3. **Fallback register line** (only rendered when the hosted keyboard is in `inspectable` mode) — `InspectRegister`, sitting directly below the keys, inside the same paper-bright panel.

**Border/elevation:** 2px solid `--color-ink` top border on the whole dock (separating it from scrolled page content), plus a subtle upward lift using the same `color-mix` technique `PianoKeyboard`'s own selected-hatch treatment already uses (no new token): `box-shadow: 0 -4px 0 color-mix(in srgb, var(--color-ink) 6%, transparent);`. This is deliberately **not** the button offset-shadow motif (`3px 3px 0 var(--color-ink)`, reserved for `Button.svelte`) — the dock is chrome, not a button, so it gets a softer, non-directional lift instead.

**Collapsed state:** only the handle bar renders (44px total height); label reads "Keyboard · tap to expand". Keyboard surface and register line are removed from layout entirely (not just visually hidden), matching sketch 008's `display: none` collapse behavior — this also stops the collapsed keyboard from doing any hidden work (no ResizeObserver measuring a display:none element, no stray audio wiring).

**Expanded state:** handle + keyboard surface + (conditionally) register line all render; label reads "Keyboard · tap to collapse".

**Safe area:** `padding-bottom: env(safe-area-inset-bottom, 0px)` on the dock's outermost element, so the handle/keys never sit under an iOS home-indicator strip on an installed PWA (this app is already an installable PWA per Phase 9's manifest work).

**Content clearance (critical, avoids the dock covering page content):** the scrollable page-content wrapper on every docked page needs a `padding-bottom` (or equivalent scroll-margin) equal to the dock's *current live rendered height* — 44px collapsed, or `44px + 160px + (register line height, ~24px, only in inspectable mode)` expanded. This value changes with collapse state and with whether the register line is showing, so it must be measured (e.g. `bind:offsetHeight` on the dock element feeding a CSS custom property or reactive padding value) rather than hardcoded as a single spacing token — hardcoding one of the two heights would either waste space in the other state or let content hide behind the dock. This is an interaction requirement, not a specific implementation; the planner owns the exact measurement mechanism.

**Motion:** collapse/expand is an instant layout change (matches sketch 008's own implementation — no slide/transition was mocked); no new animation keyframe is introduced. If a transition is added for polish, it must respect `prefers-reduced-motion: reduce` per the app's existing convention (`app.css`'s existing reduced-motion guards on `.stamp`/`.piano-keyboard__key--stamped`/`.piano-keyboard__key--pressed`).

## Known Conflict Flagged for Planner

Drills' existing short-landscape two-pane layout (Phase 09-03, `max-height: 600px and (orientation: landscape)`) already positions its keyboard pane at a fixed, always-visible location within a height-cleared `main`. Per Scope Decision 7, the new fixed dock chrome is suppressed specifically on that media-query breakpoint; the keyboard renders in its existing landscape pane instead, with the same mode-precedence rule (Decision 3) governing interactive vs. inspectable. If the planner finds this breakpoint no longer applies cleanly once Recall/Scales/Theory also gain a dock (their layouts have no existing landscape two-pane treatment), the same suppression rule should extend to any future short-landscape special-case those pages might need — this UI-SPEC does not require building new landscape layouts for Recall/Scales/Theory; today they have none, and none is introduced by this phase.
