## Pulse & Auto-Play Interaction Contract

### New shared keyframe (add to `src/app.css`, alongside the existing `stamp-in` keyframe — same file, same sharing rationale already documented there)

```css
@keyframes pulse-once {
	0% {
		transform: scale(1);
		filter: brightness(1);
	}
	40% {
		transform: scale(1.05);
		filter: brightness(1.1);
	}
	100% {
		transform: scale(1);
		filter: brightness(1);
	}
}

.pulse-once {
	animation: pulse-once 200ms ease-out;
}
```

- **Duration: 200ms**, ease-out (per D's "~200ms" guidance) — deliberately shorter than the existing 240ms `stamp-in`, so it reads as a quick "flex," not a second entrance.
- Applies identically to `PianoKeyboard` keys and to the `ChordGlyph` wrapper — ONE shared keyframe, not two (resolves the Claude's Discretion note explicitly: one keyframe, reused).
- Add `.pulse-once` and any new pending/lit state classes below to the existing `@media (prefers-reduced-motion: reduce)` rule in `app.css` (see Reduced Motion section).

### Why the pulse must be SEQUENCED, not concurrent, with `stamp-in` on first reveal

Both `stamp-in` and `pulse-once` animate `transform`. Two CSS animation classes applied to the same element at the same instant would collide (only one `animation` shorthand wins per element) — this is precisely the sketch's "pulse must not fight stamp-in" warning made concrete. The fix: on the FIRST reveal only, give the combined rule two comma-separated animations with the pulse delayed to start exactly as the entrance finishes:

```css
/* First-reveal only: stamp-in plays 0-240ms, pulse-once starts at 240ms. */
.piano-keyboard__key--stamped.pulse-once,
.chord-glyph--stamped.pulse-once {
	animation:
		stamp-in 240ms ease-out,
		pulse-once 200ms ease-out 240ms;
}
```

This satisfies D-02/D-03's "fired in the same tick as `playChord`" as: **triggered** in the same tick (both scheduled by the same `sessionState → 'complete'` transition), while the pulse's *visible peak* lands right as the entrance settles — a second beat, not a fight. Audio (`playChord`) itself fires at t=0 with no delay; Tone's `lookAhead = 0` already makes it feel instantaneous, so the sound and the settle-then-flex read as synced.

### Timing tables

**Initial reveal (sessionState transitions to `complete`):**

| Sound | Study mode | What happens |
|-------|-----------|----------------|
| ON | OFF | t=0: `playChord(earnedNotes)`. t=0-240ms: glyph + keys stamp-in (existing, unchanged). t=240-440ms: glyph + all lit keys pulse-once together. |
| ON | ON | t=0-240ms: stamp-in (unchanged), no pulse yet. t=260/520/780/1040ms: each note of `earnedNotes` (in construction order = root→3rd→5th→7th) sounds via `playArpeggio` and its key transitions pending→lit + pulses (delay 0 at its own tick — stamp-in has already finished by 260ms so no collision). t=1300ms: `playChord(earnedNotes)` block strike + pulse-once on ALL keys + glyph together. |
| OFF | OFF | Same visual timing as ON/OFF above (stamp-in 0-240ms, single pulse 240-440ms), no audio call. |
| OFF | ON | **Same as OFF/OFF** — single visual pulse only, no roll, no per-note sequence (D-07: sound off always collapses to the plain single pulse, regardless of study toggle. Never fake a silent roll). |

**"Hear again" replay (D-09/D-10) — no stamp-in running, so no delay is needed:**

| Sound | Study mode | What happens |
|-------|-----------|----------------|
| ON | OFF | t=0: `playChord` + pulse-once on keys + glyph, immediately (no 240ms wait — nothing is entering). |
| ON | ON | t=0/260/520/780ms: roll notes (shifted earlier by 260ms vs. the initial reveal, since there is no entrance to wait out). t=1040ms: block strike + full pulse. |
| OFF | OFF or ON | Single visual pulse only, immediately (t=0), silent. Never disabled (D-10). |

**Guard against re-fire on re-render:** the initial-reveal pulse/auto-play must fire exactly once per transition into `complete` (mirror the existing `recordConstructionOutcome` "fires exactly once" guard pattern already in this file) — never on an unrelated re-render while already in `complete`.

## Arpeggio Roll Contract (study mode only)

- **Order:** `construction.earnedNotes` array order, verbatim (already root→3rd→5th→7th by construction — no separate role-sort needed).
- **Stagger:** 260ms between each note's sound (D-06), first note at t=260ms on initial reveal / t=0 on replay (see timing tables above).
- **Per-key visual state before its turn ("pending"):** the key already shows its final interval-color fill (unchanged `piano-keyboard__key--{role}` class), dimmed via a new modifier:

```css
.piano-keyboard__key--pending {
	opacity: 0.28;
}
```

- **At its stagger tick:** remove `--pending` (opacity animates 0.28 → 1 over 120ms ease-out, a soft cross-fade — NOT the 200ms pulse-once scale/brightness effect) AND add `.pulse-once` for the quick flex, synced to that note's `playArpeggio` tick.
- **At the block-strike tick (t=1300ms initial / t=1040ms replay):** every key (now all lit, no `--pending` remaining) plus the glyph gets `.pulse-once` together, synced to the block `playChord` call.
- **No new mono "sequence" readout line** — see Copywriting Contract's explicit scope decision above.

## Reduced Motion

Add the new classes to the EXISTING `@media (prefers-reduced-motion: reduce)` rule in `app.css` (do not create a second rule):

```css
@media (prefers-reduced-motion: reduce) {
	.stamp,
	.piano-keyboard__key--stamped,
	.pulse-once {
		animation: none !important;
	}
	.piano-keyboard__key--pending {
		transition: none;
	}
}
```

- The pulse (`pulse-once`) is purely decorative motion — fully suppressed under reduced motion, same treatment as `stamp-in` today.
- The pending→lit opacity change during the study-mode roll is FUNCTIONAL (it is how the user sees which note just sounded), not decorative — under reduced motion it still happens, just as an instant state swap (`transition: none`) instead of a 120ms cross-fade. The underlying JS stagger timing (audio-synced, not visual filler) is unaffected either way.
- Audio and the roll's stagger timing are unaffected by `prefers-reduced-motion` — that media feature governs animation/transition, not audio scheduling.
