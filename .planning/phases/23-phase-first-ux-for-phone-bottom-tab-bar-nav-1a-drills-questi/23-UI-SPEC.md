# Phase 23 — UI Design Contract

> Visual and interaction contract for Phase 23: Phase-First UX for Phone — bottom tab bar nav (1A), Drills question-first reflow (1B), glanceable+actionable Progress (1C).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This is phase 23 of a mature, shipped app (22 phases). Every token, color, and type role below is the EXISTING Print Shop system (`src/app.css`, DESIGN-01/DESIGN-02). This phase adds **zero** new tokens — it composes new layout/interaction structure entirely from the locked palette, spacing scale, and type roles. Where a genuinely new visual pattern is needed (7-day strip, accuracy bar, bottom sheet, tab bar), it is specified here precisely so the executor never has to invent color/spacing choices.

| Property | Value |

Introducing shadcn now would fragment 22 phases of consistent custom components — gate is skipped by design, not by omission. |

## Spacing Scale

Reusing the existing scale verbatim (`src/app.css` `--spacing-*`), no new tokens:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Streak-strip square gaps, accuracy-bar internal padding |
| sm | 8px | Compact strip padding, tab-bar label gaps |
| md | 16px | Default element spacing, sheet content padding |
| lg | 24px | Section padding (sheet sections, streak hero) |
| xl | 32px | Layout gaps, streak-strip square size baseline |
| 2xl | 48px | Major section breaks (unchanged desktop layout) |
| 3xl | 64px | Page-level spacing (unchanged desktop layout) |

**Exceptions (new, this phase only):**

- Bottom tab bar height: **64px** content row + `env(safe-area-inset-bottom)` padding beneath it (iOS home-indicator clearance; the app is an installed PWA per Phase 22, so this is load-bearing, not optional). Touch targets within the bar are the full 64px row height × 1/5 bar width each (well above the 44px floor).
- Phone Check button height: **~52px** (up from Button's default 44px min-height) — a scoped override class on the drills page only, per 1B. Clear grows to match visually but stays at the 44px default (secondary action).
- Phone keyboard height: **~180px** (up from the current ~160px) inside `.drill-layout__keyboard` on phone only.
- 7-day streak square size: **32px × 32px** (`--spacing-xl`), gap **8px** (`--spacing-sm`) between squares — 7 × 32 + 6 × 8 = 272px total width, comfortably under a 360px phone viewport.
- Inline accuracy bar: track height **8px**, border **1.5px** solid ink (the one non-scale-multiple value in this phase, explicitly called out in CONTEXT — used only for this hairline border, never for spacing).

**Accent (vermilion) reserved for, this phase:**
1. 7-day streak strip: a **practiced** day's stamped square fill.
2. Inline accuracy bar fill when accuracy < 50%.
3. `StreakBadge` hero numeral when streak ≥ 1 (pre-existing, unchanged).

**Active-state chrome (tab bar active tab, strip open state) is NOT vermilion.** Per CONTEXT, it reuses `LocaleToggle`'s existing active-segment treatment: **ink fill, paper text** (`background: var(--color-ink); color: var(--color-paper);`). This is a locked, non-negotiable distinction — vermilion means "practice reward/warning," ink-fill means "this is the active navigation/UI state." Do not conflate the two.

**Accuracy bar fill thresholds (CONTEXT, locked):**
- `< 50%` → `--color-vermilion` `#c8502e`
- `< 70%` → `--color-mustard` `#f0c948`
- `>= 70%` → `--color-verdigris` `#3e7d6b`

(These are the existing interval-color-language tokens, repurposed here as a semantic accuracy gradient — not new hex values.)

## Interaction Specs

### 1A — Bottom Tab Bar (phone only, `<640px`)

- **Position:** `position: fixed; bottom: 0; left: 0; right: 0;` — above page content, below any open `BottomSheet` (sheet backdrop must cover the tab bar visually while open, `z-index` ordering: content < tab bar < sheet backdrop < sheet surface).
- **Structure:** 5 flex items, equal width (`flex: 1`), each a `<button>`/`<a>` (Lookup/Drills/Recall/Songs are real links; More is a button that opens `BottomSheet`).
- **Sizing:** total bar content height 64px (well above the 44px floor), plus `padding-bottom: env(safe-area-inset-bottom)` beneath it for iOS home-indicator clearance (this app is an installed PWA, Phase 22 — non-negotiable, real devices have this inset).
- **Chrome:** `background: var(--color-paper-bright); border-top: 2px solid var(--color-ink);` (matches the existing 2px heavy-border convention used everywhere — cards, `SongFilterToggle`, masthead's own `border-b-2`). Optional 2px ink vertical dividers between the 5 items (`border-right: 2px solid var(--color-ink)` on all but the last) — recommended for visual consistency with the border-heavy Print Shop language, but not load-bearing; if omitted, rely on padding + active-fill contrast alone.
- **Label style:** `text-label font-mono uppercase`, `letter-spacing: 0.08–0.14em` (copy exact value from `LocaleToggle`/masthead-link CSS).
- **Active state:** exact reuse of `LocaleToggle`'s active-segment rule — `background: var(--color-ink); color: var(--color-paper);` on the active tab. Determine "active" the same way the masthead already does: `$page.url.pathname === link.href` (Songs/Drills/Recall/Lookup are exact-path matches; More has no single active path — it never shows as "active" itself, though the underlying `progress`/`build`/`scales`/`theory` routes could optionally highlight a generic "More" affordance state; **not required**, keep it simple — More never carries the active-fill).
- **"More" sheet contents, in order:** Build, Scales, Theory, Progress (existing `nav.*` keys, plain rows, `min-height: 44px`, left-aligned, `text-label font-mono uppercase`) → a `border-top: 2px solid var(--color-ink)` divider → the `LocaleToggle` component, centered, with some `--spacing-md` breathing room. This is the ONLY place `LocaleToggle` renders on phone (it is removed from the slimmed header).
- **Bottom padding audit:** every `main` using `min-h-screen` needs `padding-bottom: calc(64px + env(safe-area-inset-bottom))` on phone only, so content never hides under the fixed bar. Define this once as a CSS custom property (e.g. `--tab-bar-clearance: calc(64px + env(safe-area-inset-bottom))`) in `app.css` or a shared layout style, applied via a phone-only media query to every route's `main`, rather than hand-copying the calc into N files.
- **Slimmed phone header:** `brand` (existing `text-heading font-bold uppercase` span) + `StreakBadge variant="compact"` only. No nav links, no `LocaleToggle`. Desktop header is completely untouched (all 8 links + `LocaleToggle` stay, single row, `sm:`+).
- **Breakpoint precision (technical note for the executor):** Tailwind's `sm:` utilities apply at `min-width: 640px`. To avoid a 640px-exact double-render or gap, phone-only custom CSS (tab bar, strip, streak strip) should use `@media (max-width: 639.98px)` (or `@media not all and (min-width: 640px)`), NOT a literal `max-width: 640px`, which would overlap the `sm:` boundary by one pixel. This is a precision fix on top of CONTEXT's stated "640px" language, not a contradiction of it.
- **Testids:** keep `data-testid="masthead"` on the phone header row (the slimmed one) so existing assertions on brand/streak still resolve; add `data-testid="bottom-tab-bar"` and `data-testid="more-sheet"` for new e2e coverage. Update `tests/masthead.e2e.test.ts` to assert the phone/desktop split explicitly (e.g. render at two different viewport-driven states, or assert both structures exist in the DOM with the correct CSS display governing which is visible — jsdom does not evaluate media queries, so the split must be assertable via presence of both markup blocks + class names, not by simulated viewport width).

### 1B — Drills Strip (phone portrait only, `<640px`)

- **Replaces**, on phone only: the LevelPicker `<section>`, the mode-tabs `<div data-testid="drill-mode-row">` + score-register `<p data-testid="score-register">` row, and the `SongFilterToggle` block — all three currently rendered above `.drill-layout`.
- **Strip container:** single row, `border: 2px solid var(--color-ink); background: var(--color-paper-bright); padding: var(--spacing-sm) var(--spacing-md); display: flex; justify-content: space-between; align-items: center;` — visually one compact card, not three stacked ones.
- **Left side (tappable, opens the sheet):** `TIER {n} · {MODE} ▾` — `text-label font-mono uppercase`, `role="button"` or a real `<button>` wrapping the whole left half, `aria-expanded`, `aria-label` = `drills.strip.ariaOpen`/`ariaClose` depending on state.
- **Right side (display only, not tappable):** compact score register `{asked}/{total} · {correct} ✓`, same `text-label font-mono` styling as the left side, right-aligned.
- **Sheet contents (opens via `BottomSheet`), in this order:** (1) LevelPicker's FULL existing card, unmodified component, full blurb visible (never truncated) — this is the ONLY place the full LevelPicker renders on phone; (2) the mode-tabs row, full labels, unmodified markup; (3) `SongFilterToggle` with `discrete={false}` (the discrete/hover-recede treatment exists for desktop's always-visible bar competing with the drill card — inside an explicitly-opened sheet there's no such competition, and phones have no `hover` capability anyway, so the discrete variant's `@media (hover: hover)` opacity rule never fires on phone regardless); (4) the rotate-hint paragraph, unmodified copy, tucked at the bottom of the sheet instead of floating above the question card.
- **Grid change inside `.drill-layout` (phone only):** drop the `'hint'` grid-template-area row entirely (rotate hint no longer renders inline in portrait on phone — it lives in the strip's sheet now). Desktop's `@media (orientation: landscape) and (max-height: 600px)` two-pane query and its own hint-hiding rule are completely unaffected (that rule already hides the hint in landscape; this is an additional phone-portrait-specific removal, additive not conflicting).
- **Keyboard sizing (phone only):** grow `.drill-layout__keyboard`'s effective height from ~160px to ~180px. This is a sizing change on `PianoKeyboard`'s host container, not a `PianoKeyboard` component prop change — confirm with the component whether height is intrinsic (SVG/CSS-driven from key count) or a fixed container height; if intrinsic, this likely means widening key aspect ratio or padding rather than a raw height override.
- **Check button (phone only):** override `Button`'s default 44px `min-height` to ~52px via a scoped class on `.drill-controls__primary :global(.ps-button)` inside the phone media query (mirrors the existing scoped-override pattern already used for `.drill-controls__primary :global(.ps-button) { width: 100%; }`). Clear stays at the 44px default.
- **Keyboard is explicitly NOT a fixed/sticky dock.** It renders in the normal document flow via `.drill-layout`'s grid order, exactly as today — only the container above it shrinks. Re-affirming the locked prior decision ([[keyboard-inline-not-docked]]): do not reintroduce `position: fixed`/`sticky` on the keyboard under any circumstance in this phase.

### 1C — Progress: 7-Day Strip + Inline Accuracy Bars

**7-day streak strip** (inside the existing `streak-hero` card, below `StreakBadge`):

- 7 squares, oldest → today, left → right. Each square: 32px × 32px, `border: 2px solid var(--color-ink)` (matching the app's heavy-border language, not the 1.5px hairline reserved for accuracy bars).
- **Practiced day (including today if already practiced):** filled `background: var(--color-vermilion)`. Optionally apply the existing `.stamp` `stamp-in` keyframe (already in `app.css`, shared reveal beat) on initial render for a touch of the house "stamped" feel — nice-to-have, not required; if applied, respect the existing `prefers-reduced-motion` guard already wired into that keyframe's consumers.
- **Today, not yet practiced:** `border: 2px dashed var(--color-ink); background: var(--color-paper);` — an "open" square, visually distinct from a practiced square by fill+dash, not by color alone (never rely on color alone for state — this also happens to double as an accessibility win).
- **Past day, not practiced:** `border: 2px solid var(--color-ink); background: var(--color-paper);` (solid border, no fill) — distinguishable from "today, unpracticed" purely by the solid-vs-dashed border (today's dash is the one attention-getting cue; a past miss is calmer, not shameful).
- Layout: `display: flex; gap: var(--spacing-sm);` — no day-of-week labels (keeps this phase's copy surface minimal and avoids a new EN/FR label set); each square carries a translated `aria-label` per the Copywriting Contract's three streak-strip keys, with `{DATE}` substituted client-side using the existing `localDateString`-style local-calendar-date logic (never UTC, matching the project's existing day-boundary rule).
- **Server contract:** `StreakResult` (client, `src/lib/api/progress.ts` ~line 39) gains `last7: { date: string; practiced: boolean }[]` — an ordered array, oldest → today, length 7, mirroring `server/src/streak.ts`'s `practicedDates` Set derivation relative to the passed `today`. This is additive; `streak`/`practicedToday` are unchanged. Server-side unit tests should mirror the existing streak tests (edge cases: first-ever day, streak spanning fewer than 7 days of history, a gap inside the 7-day window).

**Inline accuracy bar** (`PracticeItemRow.svelte`, then `AccuracyTable.svelte`):

- Replaces the current `border-left: 4px solid var(--color-vermilion)` weak-only accent. The bar itself now renders on **every row**, not just weak ones — its color IS the weak/strong signal (a verdigris-filled bar communicates "you're fine here" glanceably; a vermilion one flags weak items without needing the separate border treatment).
- **Track:** `height: 8px; border: 1.5px solid var(--color-ink); background: var(--color-paper);` — a hairline-bordered empty track.
- **Fill:** `width: {accuracyPercent}%; height: 100%;` positioned inside the track, color per the three thresholds in the Color section above (`< 50%` vermilion, `< 70%` mustard, `>= 70%` verdigris).
- Placement: directly below or beside the existing `accuracyPercent`% text cell (`practice-row__accuracy`) — planner's call on exact DOM position, but the bar and the numeral should sit in the same table cell/row visually adjacent, not in a separate far-away column, so the glance reads as one signal.
- `practice-row--weak` class stays (drives the per-row DRILL button's visibility), but no longer drives any border styling — it becomes a pure boolean gate for the new button, not a visual-accent class.

**Per-row DRILL button** (`PracticeItemRow.svelte` only, not `AccuracyTable`'s full-stats view — CONTEXT scopes this to "weak chord items"):

- Rendered only when `isWeak && item.kind === 'chord'`.
- `Button variant="ghost"`, label = `progress.weakest.drillOne` ("Drill"/"Exercer"), `aria-label` = `progress.weakest.drillOneAria` with the item symbol interpolated (chord symbol itself never translated).
- `onclick`: `setDrillSeeds([item.item])` then `goto('/drills')` — the exact same seam `drillThese()` already uses for the bulk button, just scoped to one symbol.
- Sits inline in the row (44px min-height already guaranteed by `Button`), does not require its own new row-height rule.

**Bulk CTA rename:** `progress.weakest.cta` ("Drill these"/"Exercer ceux-ci") becomes an N-templated "Drill all {N}" / "Exercer les {N}", N = `weakest.filter(item => item.kind === 'chord').length` (the same filter `drillThese()` already applies before seeding).

**Wide-screen cap (optional, nice-to-have per CONTEXT):** `max-width: 640px` on the Progress card container so accuracy bars don't stretch absurdly on a wide desktop window. Not required for this phase to ship; flag as a follow-up if the planner has spare scope.

## Open Questions / Flags for Planner

1. **`last7` server contract exact shape.** CONTEXT specifies `{ date, practiced }[]`, oldest→today, length 7. This UI-SPEC assumes that shape is sufficient for the visual contract above (no streak-length-vs-7-day mismatch handling specified beyond "derive from the same `practicedDates` Set"). If the user's actual practice history is younger than 7 days, the earliest entries in the array will legitimately read `practiced: false` for days before the app existed for them — this reads correctly as "past day, not practiced" per the visual spec above, no special-case needed.
2. **Rename vs. new key for the bulk CTA.** Recommend adding `progress.weakest.ctaAllN` (additive) rather than mutating the existing `progress.weakest.cta` string in place, consistent with the project's own "domain files stay additive, once-touched-by-a-plan" convention (see STATE.md's repeated "additive-only" decisions across Phases 12/13/18). Planner's call at task-breakdown time.
3. **Visual-only verification gap (carried from CONTEXT):** the preview harness cannot hydrate this app (null-origin SSR limitation, per prior memory). Sheet slide transitions, tab-bar active-fill contrast, streak-strip stamped fill, and the hover-recede behavior on desktop's `SongFilterToggle` (already shipped, unaffected by this phase) must be verified via curl-SSR + CSS assertion + Vitest where possible, and explicitly flagged to the user for on-device eyeballing for anything genuinely visual (transitions, exact perceived contrast, safe-area clearance on a real notched phone).
4. **`BottomSheet` primitive scope.** This spec assumes ONE shared component serves both the 1A More sheet and the 1B strip sheet (per CONTEXT's explicit discretion note to avoid duplicating sheet mechanics). If the planner finds the two use cases diverge enough at implementation time (e.g. the strip sheet needs to preserve `LevelPicker`'s internal state differently than the More sheet's static nav-link list), a bespoke fallback is acceptable — but default to the shared primitive first.
