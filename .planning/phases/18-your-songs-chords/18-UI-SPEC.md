**Phase 18 usage:**
- SongMark text and the "FROM MY SONGS" toggle label both use **Label** role (`text-label font-mono uppercase`), letter-spacing `0.1em`–`0.14em` per the existing mono-metadata convention (matches `.song-hook__toggle`, mode chips, register lines).

## Phase-Specific Contract

### Component Inventory

**1. `SongMark.svelte` (new, shared)**

One component, imported by three call sites (Drills, Recall, Lookup). This is the single implementation SONG-01 requires — never re-implement the tag per-surface.

Props:
```ts
interface Props {
  /** Song name(s) this chord belongs to, in first-seen order from the provenance index. Empty array = render nothing. */
  songs: string[];
}
```

Rendering rule:
- `songs.length === 0` → render **nothing** (no empty tag, no placeholder — matches `SongHook.svelte`'s existing "render nothing when there's nothing to say" convention).
- `songs.length === 1` → `♪ {songs[0]}` (uppercase via CSS), single 2px solid ink border.
- `songs.length >= 2` → `{songs.length} SONGS`, same tag but `border-style: double` (matches sketch 011-A's `.prov.mult` exactly — this is the one deliberate visual escalation for the multi-song case, no other property changes).

Visual spec (all values are existing tokens, zero new CSS variables):
```css
.song-mark {
  display: inline-flex;
  align-items: center;
  gap: var(--spacing-xs);
  font: 700 var(--text-label) / 1.4 var(--font-mono);
  letter-spacing: 0.1em;
  text-transform: uppercase;
  border: 2px solid var(--color-ink);
  background: var(--color-paper);
  color: var(--color-ink);
  padding: var(--spacing-xs) var(--spacing-sm);
  white-space: nowrap;
}
.song-mark--multi {
  border-style: double;
}
```
The `♪` glyph precedes the label in the single-song case; the multi-song case shows the bare count (`2 SONGS`, no note glyph), matching the sketch precisely.

Non-goals: no click behavior, no tooltip listing every song on hover/tap in v1 (that's the deferred "name every song inline" idea) — it is a static, read-only display object.

**2. Filter toggle (new, shared pattern — not necessarily a new component)**

Discretion resolved: build as a single `<button>` following the sketch's checkbox-style toggle exactly, not the app's two-way segmented `Button aria-pressed` pattern used for Review/Map or Chords/Intervals/Mix — those are N-way mode switches, this is a single binary on/off filter, and the sketch's dedicated checkbox-box treatment reads more clearly as "a filter you can flip" than another mode tab would.

```css
.song-filter-toggle {
  font: 700 var(--text-label) / 1.4 var(--font-mono);
  letter-spacing: 0.08em;
  text-transform: uppercase;
  border: 2px solid var(--color-ink);
  background: var(--color-paper);
  color: var(--color-ink);
  padding: var(--spacing-sm) var(--spacing-md);
  min-height: 44px;
  cursor: pointer;
  display: inline-flex;
  align-items: center;
  gap: var(--spacing-sm);
}
.song-filter-toggle[aria-pressed="true"] {
  background: var(--color-vermilion);
  color: var(--color-paper);
  border-color: var(--color-ink);
}
.song-filter-toggle__box {
  width: 14px;
  height: 14px;
  border: 2px solid currentColor;
  display: inline-block;
}
.song-filter-toggle[aria-pressed="true"] .song-filter-toggle__box {
  background: var(--color-paper);
}
```
Markup: `<button class="song-filter-toggle" aria-pressed={filterOn} onclick={...}><span class="song-filter-toggle__box"></span>From my songs</button>`, wrapped in a `.filterbar`-style container (2px ink border, `--color-paper-bright` background, `space-between` layout with the pool label) reusing the sketch's `.filterbar` shape almost verbatim.

**3. Provenance index (new, logic module — not a component but load-bearing for every surface above)**

Location: `src/lib/practice/songProvenance.ts` (discretion-resolved location, sibling to `songs.ts`).

Contract:
```ts
/** symbol -> song names that contain it, first-seen order, ACTIVE songs only. */
export function buildProvenanceIndex(): Map<string, string[]>;
/** Convenience lookup a component calls directly; normalizes both sides via the theory engine before comparing (Cm7 === C-7 === Cmin7). */
export function songsForSymbol(symbol: string, index?: Map<string, string[]>): string[];
```
Matching is by normalized chord identity (reuse `spellChord`/theory engine's own normalization — never raw string equality), per the locked SONG-03 decision. Built once from `listSongs().filter(s => s.active)`; surfaces call `songsForSymbol()` per rendered chord.

### Surface Placement (SONG-01)

| Surface | Anchor point | Notes |
|---------|--------------|-------|
| Drills prompt | Directly below the question/prompt text, centered, above the keyboard/choice controls (matches sketch 011-A's `.prompt .provrow`) | Shows for both construction and identification question types whenever the drawn symbol has provenance, filter state notwithstanding |
| Recall — mode `formula` | Beside the `ChordGlyph` in `recall-prompt`, shown immediately (pre-reveal) — the symbol itself is already visible in this mode, so the mark is never a spoiler | |
| Recall — mode `see-play` | Beside the `ChordGlyph` in `recall-prompt`, shown immediately (pre-answer) — same reasoning, symbol is the given, not the answer | |
| Recall — mode `hear-name` | **Never shown before the user answers.** The 4 choice buttons ARE the candidate answers; marking one would leak it. Show it only after `hearNameAnswered`, beside the disclosed correct symbol (the `RevealInsight`/confirmation block) | Explicit spoiler-safety rule — new for this phase, not previously a concern |
| Recall — mode `formula-build` (embedded BuildSession) | Beside BuildSession's `ChordGlyph`, shown immediately — this mode's task is building notes from a known symbol, not guessing the symbol, so no spoiler risk | Standalone `/build` (outside Recall) is out of this phase's required scope but may reuse the same mark for free if trivial |
| Chord Lookup result | Inline in the result header, beside the chord name (matches sketch 011-A's `.lookup-result .head`) | Shown for any successfully resolved symbol with provenance, regardless of filter state (Lookup has no filter — SONG-02 only applies to Drills/Recall) |

### Filter Placement & Behavior (SONG-02)

| Surface | Placement | Persistence key |
|---------|-----------|------------------|
| Drills | A `.filterbar`-style bar above the prompt card, matching sketch 011-A: pool label left, toggle right | `music-learn:drills-song-filter` (boolean, localStorage, per established `music-learn:*` naming) |
| Recall | Same bar shape, placed above the mode chip/register line on the Review surface only (not shown on the Map surface — the map already visualizes the whole fact set) | `music-learn:recall-song-filter` (boolean, localStorage, separate key — the two surfaces persist independently per the locked "per-surface" decision) |

Default: **off** on both surfaces (locked). Toggling filters the underlying pool/queue construction (`PoolContext.songSymbols`-driven weighting on Drills already exists as a seam; Recall's `getDueCards()`/queue composition needs the equivalent restriction added, scoped to chord-formula facts whose symbol has provenance).

Edge case (locked in CONTEXT, restated here as a UI contract): filter ON + zero active songs (or zero derivable chords) → do not render an empty/dead session. Show the pool note in its "no active songs" wording (see Copywriting Contract) and silently fall back to the full, unfiltered pool/queue for that session. The toggle itself stays visually ON (reflects the user's actual choice) even though the effective pool is the full library — do not auto-flip it off.

### Accessibility

- SongMark: not interactive, no `role`/`tabindex` needed; if it ever needs a full song list on hover for the multi-song case (future work, not this phase), that would be a `<button>` not a `<span>` — v1 stays a plain inert tag.
- Filter toggle: real `<button aria-pressed>`, exactly the existing app pattern (`Button` component's `aria-pressed` usage on Review/Map, Chords/Intervals/Mix) — screen readers already handle this correctly elsewhere in the app.
- Color is never the only signal distinguishing single vs multi-song marks: the double border is a shape change, and the text itself differs (`♪ NAME` vs `N SONGS`) — no color-only distinction exists.
