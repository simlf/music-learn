    - songsForSymbol returns [] for a symbol in no song.

  <action>
    Create `src/lib/practice/songProvenance.ts` as a PURE module (no DOM, no Svelte, no localStorage key of its own) that derives everything from `listSongs()`/`activeSongChordSymbols()` in songs.ts. Follow the songs.ts module style (exported public functions, internal helpers unexported, no throwing).

    Export exactly these:
    - `normalizeSymbolForMatch(symbol: string): string` — calls `spellChord(symbol)`; returns `spelled.symbol` when `spelled.recognized`, else returns the raw `symbol` unchanged (fallback keeps unrecognized user symbols total). This is the ONE normalization seam; both index-build and lookup use it so matching is enharmonic/alias-aware per SONG-03, never raw string equality.
    - `buildProvenanceIndex(): Map<string, string[]>` — iterates `listSongs()`, skips `active === false` songs, and for each active song's `chordSymbols` adds the song NAME to the array under key `normalizeSymbolForMatch(symbol)`. Preserve first-seen order of song names and de-duplicate a song name that already appears for that key (a song listing the same chord twice must not double-list its own name).
    - `songsForSymbol(symbol: string, index?: Map<string, string[]>): string[]` — builds the index on demand when `index` is omitted (convenience for a one-off call), else uses the passed index; returns `index.get(normalizeSymbolForMatch(symbol)) ?? []`.
    - `symbolHasProvenance(symbol: string, index?: Map<string, string[]>): boolean` — thin predicate: `songsForSymbol(symbol, index).length > 0`. Recall's queue filter (Plan 03) calls this per chord-formula fact.
    - `drillableSongSymbols(): string[]` — `activeSongChordSymbols().filter((s) => spellChord(s).recognized)`; the restricted candidate universe Drills (Plan 02) draws from when the filter is ON. Recognized-only so a hand-entered/exotic song symbol never poses an unrenderable drill question.

    Document at the top (JSDoc) that this module holds NO storage of its own and is a read-only derivation of songs.ts, so it stays a single source of truth (SONG-03).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| localStorage → app | Song records (incl. user-authored song names and chord symbols) are read from `music-learn:songs`; hand-editable, may be malformed. |
| song data → DOM | Song names flow into the SongMark tag rendered on-screen. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-18-01 | Tampering/XSS | SongMark.svelte (song name → DOM) | medium | mitigate | Render the song name via Svelte text interpolation `{songs[0]}` (auto-escaped). Never `{@html}`. Uppercase is CSS `text-transform`, not string rebuilding, so a name with markup cannot inject. |
| T-18-02 | Denial of Service | songProvenance.ts (malformed store) | low | mitigate | Read songs only through `listSongs()`, which already try/catches and drops malformed entries; add no direct localStorage read here. `normalizeSymbolForMatch` falls back to raw input on an unrecognized symbol (never throws). |
| T-18-SC | Tampering (supply chain) | npm installs | low | accept | This phase installs NO packages (all primitives reuse existing tonal/Svelte/testing-library). Package legitimacy gate not triggered; no [ASSUMED]/[SUS] packages. |
</threat_model>
