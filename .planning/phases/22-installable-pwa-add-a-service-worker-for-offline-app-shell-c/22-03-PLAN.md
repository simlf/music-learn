<objective>
Close the PWA update loop: when a new version is deployed and its service worker is waiting to activate, show a gentle bilingual "update available, reload" prompt instead of trapping the user on the stale cached build. On confirm, tell the waiting worker to skipWaiting and reload once on `controllerchange`. Never reload silently mid-session. The reload/update state lives in a small `.svelte.ts` module with a pure, unit-testable core; the UI is a lightweight `UpdatePrompt.svelte` mounted once in the root layout; the copy is bilingual via the existing i18n chrome domain.

Purpose: PWA-03 — new-version update prompt (the standard SW update flow).
Output: `src/lib/pwa/swUpdate.svelte.ts` (+ test), `src/lib/components/UpdatePrompt.svelte`, bilingual copy in `chrome.ts`, and the mount + watcher wiring in `+layout.svelte`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client update flow → SW | The prompt posts a control message asking the waiting worker to activate. |
| SW activation → page | A controllerchange triggers a page reload. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-06 | Denial of Service | controllerchange reload loop | medium | mitigate | Guard the reload with a one-shot `reloaded` flag so controllerchange reloads the page exactly once, never in a loop. |
| T-22-07 | Tampering | stale-build trap (availability) | medium | mitigate | The update prompt guarantees the user can always leave a stale cached build; applyUpdate only runs on explicit user confirmation. |
| T-22-08 | Elevation of Privilege | applyUpdate postMessage | low | accept | Posts only the fixed same-origin `{ type: 'SKIP_WAITING' }` to the app's own waiting worker; no external input, benign activation. |
</threat_model>
