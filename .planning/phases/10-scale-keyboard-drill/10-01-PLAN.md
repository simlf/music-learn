<objective>
Create the pure, DOM-free logic that backs the new scale keyboard drill: a 15-target ascending-then-descending sequence graded by pitch class (chroma), plus an ascending key-placement helper that positions each scale degree on a fixed 2-octave C-to-C keyboard with the tonic as the leftmost highlighted key and the octave (degree 8) as a distinct higher key.

This replaces the letter-equality grading in the retired `scaleDrill.ts` (deleted in plan 10-02) with chroma grading, mirroring the app's existing octave-agnostic precedent `gradeIntervalTap` (SCALE-04, v2.0 cross-cutting constraint: grade by chroma/MIDI, never letter strings).

Purpose: enharmonic scales grade correctly (F♯ major's E♯ accepted on the F key) and the ascending run ends on a genuinely distinct octave key. Isolating this in a pure, unit-tested module keeps the tricky octave-placement correctness under test before any UI is built.
Output: `src/lib/practice/scaleKeyboardDrill.ts` and its passing test file.
</objective>

Design decision recorded here (discretionary point resolved): grading scope is chroma / pitch-class, octave-agnostic — a tap on ANY visible key whose chroma equals the expected degree's chroma is accepted; a wrong pitch class is never accepted. Rationale: the forced 2-octave board shows some pitch classes more than once; requiring the exact octave instance would reject a correct-pitch-class tap on the wrong octave, contradicting "grade by pitch class" and the app-wide octave-agnostic precedent (matchChord, gradeIntervalTap). The canonical fill position is still deterministic (see placeAscendingScaleKeys), so the ascending highlight grows predictably left-to-right regardless of which octave instance the finger hits.
