# Phase 10 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope:** Replace the `/scales` Practice surface's degree-ladder tap drill (`ScalePractice.svelte` + `scaleDrill.ts`) with a movable, tonic-anchored `PianoKeyboard` drill: tap the scale ascending then descending, graded by pitch class (not letter string), ending back on the tonic having touched the octave (degree 8). The Explore surface (`ScaleDegreeStrip` + `InspectRegister`) and the shared tonic row / Explore-Practice mode toggle are unchanged (SCALE-05). All tokens, interval colors, typography, spacing, and `PianoKeyboard` itself are LOCKED by Phases 1-9's UI-SPECs / `src/app.css` and are extended here, never redefined.

**Sources:** No `10-CONTEXT.md` or `10-RESEARCH.md` exist yet (this UI-SPEC was generated directly from `/gsd-ui-phase`, ahead of `/gsd-discuss-phase 10` and `/gsd-plan-phase 10`). Discretionary calls below are marked explicitly and should be confirmed, not silently overridden, once discuss/plan run. Grounded in: `.planning/ROADMAP.md` (Phase 10 goal + success criteria), `.planning/REQUIREMENTS.md` (SCALE-04, SCALE-05, v2.0 cross-cutting constraints), `src/app.css` (implemented token contract), `src/lib/components/PianoKeyboard.svelte` (component to reuse, incl. `keyboardLayout.ts`'s `assignNotesToKeys` wrap-around behavior), `src/routes/scales/+page.svelte` (Explore surface + shared tonic row, unchanged), `src/lib/components/ScalePractice.svelte` + `src/lib/practice/scaleDrill.ts` (the degree-ladder surface being retired — its letter-string `gradeTap` equality is exactly the pattern SCALE-04 replaces with pitch-class grading), `src/lib/drills/generateIntervalQuestion.ts`'s `gradeIntervalTap` (the app's existing chroma-grading precedent to follow instead), `.planning/phases/03-on-screen-drill-loop/03-UI-SPEC.md` (structural precedent for this document).

## Design System

| Property | Value |
|----------|-------|

| Icon library | none — typographic glyphs only (♯, ♭), per Phase 1 |
| Font | Same three system stacks as every prior phase, no additions: UI sans (`--font-sans`), chord/note serif (`--font-serif`), data mono (`--font-mono`) |

**New/changed components this phase:**

| Component | Contract |
|-----------|----------|
| `ScaleKeyboardDrill` (new; replaces `ScalePractice.svelte`) | Renders the movable tonic-anchored `PianoKeyboard` in `interactive` mode. On each key tap: grade by pitch class (`Note.chroma`, mirroring `gradeIntervalTap`'s existing pattern, never `tappedLetter === expectedLetter` string equality) against the currently-expected scale degree in the ascending-then-descending sequence. A correct tap fills that key immediately with its degree-role interval color (root/second/third/fourth/fifth/sixth/seventh — the same seven tokens `ScaleDegreeStrip` already uses) and a `NoteLabel`; an incorrect tap gives a brief (~320ms) gray flash on the tapped key only (reusing `--color-wrong`) and does not advance — no text headline, per Success Criterion 4's "wrong-key flash" (visual-only, momentary, matches `ScalePractice`'s existing wrong-flash discipline). Each tap plays its note (existing `playNote`/`toAscendingPitches` pattern from `ScalePractice`, carried over unchanged). No Check/Clear step: every tap grades instantly, same immediacy as the interval-construction drill (single tap = complete answer), not the multi-select chord-construction drill. |
| `PianoKeyboard` forced two-octave override (discretionary, this phase only) | The scale drill **always renders 2 octaves** (`octaves={2}`), overriding the component's normal responsive 1-octave-on-phone default. Rationale: Success Criterion 1 requires the tonic (leftmost highlighted key) and the octave/degree-8 (same pitch class, one octave up) to be two visually **distinct, individually tappable keys** — collapsing them onto one wrapped key (the existing 1-octave wrap-around fallback used by chord/interval drills, where a single pitch-class instance is enough) would make "ending on the octave" untappable as its own event. On viewports narrower than the existing 2-octave width breakpoint (~660px), wrap the keyboard in a horizontally scrollable container (`overflow-x: auto`, `-webkit-overflow-scrolling: touch`) rather than shrinking keys below the 44px touch-target floor (PLAT-01, locked). Auto-scroll so the tonic key sits at the visible left edge on load and after "Run it again." |
| Position register (new; replaces the retired 1-7 rung ladder) | A single Label-role mono status line above the keyboard, same visual family as the Drills page `ScoreRegister` (uppercase mono, no bar background, neutral not alarm-colored). Format: `DEGREE {n} OF 8 · {DIRECTION}` (see Copywriting Contract for exact strings and direction values). This is the drill's only "progress" affordance beyond the keys' own fill state — no separate ladder/progress-bar widget is reintroduced (SCALE-05's "no keyboard-vs-ladder toggle" reads as "the ladder representation is retired entirely," so a ladder-shaped progress widget is avoided even as a non-toggled companion). |
| Completion card | Reuses the Print Shop bordered-card pattern (`border-ink bg-paper-bright`) already used by `ScalePractice`'s `.complete` block and the Drills end-card: one status line + a primary `Button` labeled `Run it again` (verbatim reuse of the existing established phrase, not a new string). No stamp/confetti flourish beyond the existing `.stamp` keyframe reused for the card's entrance, matching the app-wide "the fill is the reward" restraint principle. |

## Copywriting Contract

Tone: warm print-shop-clerk voice, unchanged from every prior phase (fun, witty, never scolding, occasional French winks, uppercase mono for status lines). **No em dashes anywhere** — periods, colons, commas only. Mid-dot (`·`) is the established status-line separator, not an em dash.

| Element | Copy |
|---------|------|
| Instruction line (drill start) | `Play {tonic} major ascending, then descending.` |
| Position register, ascending | `DEGREE {n} OF 8 · ASCENDING` (n counts 1 to 8) |
| Position register, descending | `DEGREE {n} OF 8 · DESCENDING` (n counts 8 down to 1) |
| Wrong tap | none — visual flash only, no text, per Success Criterion 4 and existing `ScalePractice` precedent |
| Completion status line | `Voila. {tonic} major, up and down, clean.` (echoes `ScalePractice`'s existing `Voila. {tonic} major, clean.`, extended for the new ascending-and-descending scope) |
| Reset/replay button | `Run it again` (verbatim reuse of the existing Drills end-card phrase, not a new string) |
| Empty state | not applicable — a tonic is always already selected via the shared tonic row above the mode toggle; the drill is never shown with nothing to practice |
| Error state | not applicable — no network/data fetch in this drill (pure client-side theory), so no error copy is needed |
| Destructive confirmation | not applicable — no destructive action exists; "Run it again" discards only in-progress, ungraded drill state (matches the existing D-10-style "ephemeral, no confirmation" rule already applied to the Drills score register) |

## Layout Contract (new this phase)

Vertical stack inside the existing Practice-mode card (the shared bordered card, mode toggle, and tonic row above it are unchanged from `/scales`' current structure):

1. Instruction line (Body role)
2. Position register (Label role, mono, `sm` gap below instruction)
3. `PianoKeyboard` (interactive, forced 2 octaves, horizontally scrollable below the ~660px breakpoint), `sm` gap below the register
4. Completion card (only once all 15 taps land correctly — 8 ascending + 7 descending; replaces items 1-3 in place, does not stack below them, mirroring `ScalePractice`'s existing "complete" swap behavior rather than the Drills page's separate end-card)

Interaction flow (restates Success Criteria 1, 2, 4 as the visual/interaction spec):
- The keyboard is interactive from the moment Practice mode is entered (no separate "start" tap needed) — same zero-friction rule as the Drills loop.
- Grading is chroma/pitch-class based (SCALE-04): a tap on any key whose pitch class matches the expected next degree is correct, regardless of its enharmonic spelling or which octave instance is tapped (e.g., Gb major's Cb degree is accepted whether the visible key is spelled Cb or B, and whether the user's finger lands on either octave instance of that pitch class, since the tonic-anchored two-octave layout may present the same pitch class more than once outside the exact expected key — planner's call on whether to constrain taps to the single "expected" key position or accept any matching pitch class on the visible board; this UI-SPEC only requires that whichever key IS accepted fills with the correct degree color and never accepts a wrong pitch class).
- Changing the tonic (shared row) or switching back to Explore and returning resets the drill to degree 1, ascending — same "fresh state on prop change" rule `ScalePractice` already implements via its `$effect` reset.
- No auto-advance past completion: the completion card's `Run it again` is the only way to restart; reaching it is the drill's sole "pass" signal (Success Criterion 4).

## Implementation Notes for Planner/Executor

- Replace `ScalePractice.svelte` and retire `scaleDrill.ts`'s letter-equality `gradeTap`/`expectedLetter`/`createScaleDrillState` (or rewrite them to grade by chroma) — the v2.0 cross-cutting constraint ("grade notes by chroma/MIDI never letter strings") makes the current `tappedLetter === expectedLetter(state)` string comparison a defect to fix, not a pattern to preserve. Follow `generateIntervalQuestion.ts`'s `gradeIntervalTap` as the precedent (`Note.chroma` comparison, octave-agnostic).
- The ascending-then-descending sequence is 15 graded taps: degrees 1→8 ascending, then 7→1 descending (degree 8 is tapped once, not twice). Model this as a flat ordered list of 15 expected pitch classes (or reuse/extend a state-machine shape like the retired `ScaleDrillState`, chroma-based) rather than two separate 7/8-step sub-drills, so a single position counter drives both the register and the "done" check.
- `PianoKeyboard`'s existing `octaves` prop already supports a `2` override (used elsewhere for explicit test seams); passing it here is additive and needs no component API change. The horizontal-scroll wrapper is new: a plain `overflow-x: auto` container around `PianoKeyboard`, sized to its natural 2-octave width, with a scroll-into-view call (`scrollIntoView({ inline: 'start' })` on the tonic key, or an equivalent ref-based scroll) on mount and on reset.
- The per-key "correct tap fills immediately" behavior does not yet exist on `PianoKeyboard` in this exact shape (today's `interactive` mode only tracks a `selected` hatch state until an external Check step, and `wrongLetters` is a batch feedback-mode signal, not a live per-tap transient flash). This phase likely needs either: (a) a new lightweight prop pair on `PianoKeyboard` for "confirmed-correct letters + their degree role" and "transient-wrong letter," or (b) a small drill-specific wrapper that tracks per-key state itself and passes already-graded `notes` (interval-colored) to a read-only `PianoKeyboard` for confirmed keys while overlaying its own transient wrong-flash styling. Planner's call which shape fits the existing component contract best; this UI-SPEC only fixes the visual outcome (immediate color fill on correct, momentary gray flash on wrong, no Check step).
- Reuse `playNote`/`toAscendingPitches` (`$lib/audio/voicing`, `$lib/audio/audio`) exactly as `ScalePractice.svelte` already does — no new audio logic needed.
- No new CSS custom properties are needed in `src/app.css`; every color/spacing/typography token used here already exists. The horizontal-scroll container and the transient wrong-flash treatment are component-scoped CSS, not new design tokens.
- `ScaleDegreeStrip`, `InspectRegister`, the shared tonic row, and the Explore/Practice mode toggle in `src/routes/scales/+page.svelte` are unchanged (Success Criterion 3) — only the `{:else}` branch currently rendering `<ScalePractice />` is replaced with the new `ScaleKeyboardDrill` (or equivalent) component.
