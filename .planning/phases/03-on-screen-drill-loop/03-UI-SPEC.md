# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope:** A `/drills` page delivering an interleaved practice loop in both chord-fluency directions: construction (symbol shown, click the notes) and identification (notes highlighted, pick the symbol from 4 options). Covers the interactive/selectable `PianoKeyboard` mode, Check/Clear affordances, multiple-choice layout, right/wrong feedback (reusing the Phase 1 stamp beat and interval-color language), the in-session score register, and the new Drills nav link. All tokens, interval colors, typography, spacing, and core components are LOCKED by `01-UI-SPEC.md` / `02-UI-SPEC.md` / `src/app.css` and are extended here, never redefined.

**Sources:** `.planning/phases/03-on-screen-drill-loop/03-CONTEXT.md` (D-01..D-13, all decisions locked, autonomous run), `.planning/phases/01-print-shop-foundation-theory-core/01-UI-SPEC.md` (locked visual contract, interval colors), `.planning/phases/02-chord-lookup-companion/02-UI-SPEC.md` (masthead/nav pattern, 44px touch targets, copy register), `.planning/phases/01-print-shop-foundation-theory-core/01-CONTEXT.md` (D-01..D-12 tone/motion/feedback), `src/app.css` (implemented token contract), `src/lib/components/PianoKeyboard.svelte` (keyboard to extend), `src/routes/+page.svelte` (feedback/composition patterns reused).

**New components this phase** (extend Phase 1/2's set, reuse its tokens):

| Component | Contract |
|-----------|----------|
| `PianoKeyboard` interactive mode (extends existing component, D-11) | Add an `interactive` mode prop (default `false`, preserving Phase 1/2's display-only behavior unchanged). In interactive mode: every key gets a click/keydown (Enter/Space) handler and `role="button"` + `aria-pressed`; clicking toggles a `selected` boolean per key, independent of any `note`/interval-role highlight data. Selected-key visual treatment is a **diagonal ink hatch pattern** (repeating 45° hairline stripes, `--color-ink` at low opacity over the key's base fill) plus a solid 2px inset ink border, applied identically to white and black keys. This is deliberately NOT a color fill (no vermilion/verdigris/tan/mustard) so it can never be confused with the four reserved interval colors, which appear only on revealed/correct notes (D-11 requirement). Selected white keys keep their `--color-paper-bright` base; selected black keys keep `--color-ink` base (hatch renders in `--color-paper-bright` at low opacity on black keys, inverted, so the pattern stays visible on both key colors). No `NoteLabel` renders on a merely-selected key in the construction drill's "before Check" state (the shop does not tell you what you clicked, only whether it's a real note. Revealing the letter is what "revealed/correct" feedback is for). In identification-drill mode (notes pre-highlighted, keyboard read-only for that phase of the question) the keyboard renders exactly as Phase 1/2's display-only mode: interval colors, `NoteLabel`s, no click handlers. |
| `DrillCard` (page shell) | The Print Shop `stamp`-bordered card pattern from showcase/lookup (`border-2 border-ink bg-paper-bright` sectioned block), holding one question at a time: prompt row, keyboard, action row, feedback row. Reuses the existing `.stamp` keyframe for the feedback reveal (right or wrong), never a new animation. |
| `DrillPrompt` | Construction: renders the target `ChordGlyph` (reused from Phase 1, same serif/shadow treatment) plus the instruction line `Click the notes for {symbol}.` in Body role. Identification: renders the keyboard pre-highlighted with the mystery chord's notes in interval colors (root/3rd/5th/7th, exactly like lookup) plus the instruction line `Name this chord.` in Body role. No chord symbol text is shown during an identification question (that would give away the answer). |
| `AnswerActions` (construction only) | Two buttons, `Button` component reused: `Check` (primary, vermilion) and `Clear` (ghost). Row layout: `gap: sm`, both meet the 44px minimum. `Check` is disabled (ghost-styled disabled state: reduced opacity, no shadow, `cursor: not-allowed`) until at least one key is selected, preventing an empty-answer submit. `Clear` is always enabled once any key is selected; deselects all keys and returns to the pre-answer state without advancing the question. |
| `ChoiceGrid` (identification only) | 4 `Button` ghost-variant options in a 2x2 grid on mobile portrait (single column below 360px width), 4-across row on wider viewports. Each option shows a chord symbol in `ChordGlyph`'s serif family but at Heading size (20px, not the 56px Display size reserved for the question/result glyph) so all 4 fit without the print-shadow flourish (that stays exclusive to the primary displayed chord, per Phase 1's "reserved for" discipline extended here: no fourth-quadrant use of the misregistered-shadow motif). Options are unstyled for correctness before answering (no color-coding a right/wrong guess ahead of time); tapping one immediately submits (no separate Check step for identification, since the "answer" is a single discrete choice, not an assembled set — D-05 already specifies multiple choice as the format). Each option meets 44px minimum height via padding. |
| `FeedbackBanner` | Right answer: reuses the exact Phase 1 `.stamp` scale-in, no new banner chrome, plus a single warm confirmation line in Body weight 700 reusing showcase's restraint principle (the stamp IS the reward, D-07 from Phase 1 carries forward). Copy: `Nailed it.` (see Copywriting Contract). Wrong answer: inverted ink bar (`bg-ink`, matches the existing error-bar treatment from Phase 1/2) containing: (1) a Label-size mono headline in mustard text (`Not quite.`), (2) the correct notes re-rendered on the keyboard in full interval colors with `NoteLabel`s (the teaching reveal), (3) the interval-formula chip row (`IntervalChip` + dual-named notes, exact reuse of `formulaFor`), (4) for construction drills only, a compact "you played / correct" diff line (see below). `Next` button (primary) appears below the banner to advance; auto-advance is never used (D-07 from 03-CONTEXT). |
| `PlayedVsCorrectDiff` (construction wrong-answer only) | Two label:value rows in mono Label size: `You played:` followed by the user's selected pitch-class letters (joined, e.g. `C, E♭, G`), `Correct:` followed by the target chord's spelled notes (joined, e.g. `C, E♭, G, B♭`). Extra notes the user played that aren't in the target are visually marked by wrapping them in a plain ink-bordered `IntervalChip`-sized tag with no fill (mirrors "not a real answer" without inventing a new red/negative color, keeping D-DESTRUCTIVE discipline of "no new red"). Missing notes (in target, not played) need no special mark since they're already shown revealed in interval colors on the keyboard above. |
| `ScoreRegister` | Sits in the existing uppercase mono status-bar register (same visual family as the Phase 1/2 error bar, but not inverted/alarm-colored since this is neutral running status, not an error). Rendered as plain Label-size mono text on the paper ground (no bar background), right-aligned on desktop, full-width centered on mobile, positioned above the `DrillCard` at the top of the page (below the page heading). Format: `{correct} RIGHT · {streak} STREAK` (see Copywriting Contract for exact separator glyph choice, mid-dot not em dash). In-memory only, per D-10; resets silently on reload with no confirmation (nothing destructive is being discarded, it's ephemeral session state, not a deletion the user asked for). |
| Masthead nav link addition (D-13) | Extends `+layout.svelte`'s existing `navLinks` array with `{ href: '/drills', label: 'Drills' }` inserted after Lookup, before Showcase. Zero new visual contract: identical `masthead__link` styling, active-state underline, hover/focus treatment already defined in Phase 2. |

## Spacing Scale

Declared values (must be multiples of 4) — identical to Phase 1/2, no new tokens needed:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Chip internal padding, diff-row label-to-value gap |
| sm | 8px | Gaps between Check/Clear buttons, gaps between choice-grid cells, nav link gaps |
| md | 16px | Default element spacing, DrillCard internal padding, prompt-to-keyboard gap |
| lg | 24px | Section padding inside DrillCard (prompt block, action block, feedback block separated by `lg`) |
| xl | 32px | Gap between ScoreRegister and DrillCard, gap between DrillCard and page heading |
| 2xl | 48px | Page top/bottom padding (desktop) |
| 3xl | 64px | Max page-level spacing (large screens) |

Exceptions (carried from Phase 1/2, still apply):
- 2px borders (DrillCard, buttons, masthead) and 1.5px keyboard key borders.
- 3px offset shadows (buttons, misregistered chord glyph shadow on the question/result display only, never on ChoiceGrid options).
- 44px minimum touch target — load-bearing this phase for every keyboard key in interactive mode, both `Check`/`Clear` buttons, all 4 `ChoiceGrid` options, and the `Next` button.

New exception:
- **Above-the-fold budget for the primary loop (explicit, load-bearing this phase per the phase constraint):** on a phone in portrait (iPhone SE baseline, 375×667), the question-answer-feedback loop (ScoreRegister + DrillPrompt + keyboard + action row, i.e. everything needed to answer without scrolling) must fit above the fold. If the stack exceeds viewport height, reduce `ScoreRegister`'s top/bottom margin and `DrillCard`'s internal section gaps from `lg` (24px) to `md` (16px) first; only if still overflowing, reduce the page-heading (`Drills`) top margin from `md` (16px) to `sm` (8px). No spacing value is reduced below `sm` (8px); this two-step reduction is the only conditional spacing in this spec, and all other spacing values are unconditional. The keyboard itself, its key sizing, and all type sizes are never trimmed (same discipline as Phase 2's mobile-portrait exception). The interval-formula chip row and `PlayedVsCorrectDiff` in the wrong-answer feedback may sit below the fold (secondary elaboration, revealed only after answering, not part of the initial above-the-fold question view).

## Typography

Exactly 4 sizes, 2 weights (400, 700) — unchanged from Phase 1/2, no new roles:

| Role | Size | Weight | Line Height | Family |
|------|------|--------|-------------|--------|
| Body | 16px | 400 | 1.5 | UI sans — instruction lines (`Click the notes for...`, `Name this chord.`), diff-row values |
| Label (data/mono) | 12px | 700 | 1.4 | Mono — ScoreRegister, feedback headlines (`Not quite.` in the inverted bar), interval-formula chips, diff-row labels, nav links (unchanged) |
| Heading | 20px | 700 | 1.2 | UI sans — page heading (`Drills`), ChoiceGrid option chord symbols (serif per note below) |
| Display (chord glyph) | 56px | 700 | 1.05 | Serif — the question chord glyph (construction drills) and the revealed-correct chord glyph (wrong-answer feedback), unchanged from Phase 1 |

Notes:
- ChoiceGrid options render chord symbols in the serif family (`--font-serif`) at Heading size (20px, not Display 56px) and Heading weight (700) — this is a font-family override within the existing Heading role bounds, not a new fifth size. The misregistered print-shadow effect is exclusive to Display-size glyphs (per Phase 1's "reserved for" discipline) and does NOT apply to ChoiceGrid options.
- `Nailed it.` (right-answer confirmation) renders at Body weight 700 inside the stamp block, sized at Body (16px) — reuses the Body role, bolded for emphasis per Phase 1's "emphasis via weight, not new sizes" rule.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f2ecdd` (paper) | Page background, DrillCard surface — unchanged |
| Secondary (30%) | `#faf6ea` (bright paper) + `#221e17` (ink) | White keyboard keys, DrillCard border/dividers, all borders/black keys/text — unchanged |
| Accent (10%) | `#c8502e` (vermilion) | See reserved-for list below — unchanged budget, one new usage added this phase |
| Muted text | `#7d7462` | Instruction lines, diff-row labels, secondary copy |
| Faint labels | `#9a907f` | Unhighlighted/unselected note labels (unchanged) |
| Destructive | none this phase | `Clear` is not destructive in the confirmation sense (it discards an in-progress, ungraded answer, not a saved result) — no confirmation dialog, no red. See Copywriting Contract. |

Accent (vermilion `#c8502e`) reserved for — exhaustive list, extends Phase 1/2's list with exactly one new entry:
1. Primary button background (`Check` button, `Next` button — same primary `Button` variant already defined, no new usage pattern)
2. Misregistered print shadow behind chord glyphs (question glyph, revealed-correct glyph)
3. Root interval color (unchanged, keyboard highlights + interval chips)

Never use vermilion for: the selected/pending key state (this is the phase's key discipline point, see below), `ChoiceGrid` options before or after answering, `Clear` button (ghost variant, ink only), ScoreRegister text, nav links, focus rings, hover states.

**Selected/pending key vs. interval-color / revealed-correct key (the phase's core visual distinction, per constraint 2 and D-11):**
- Selected (pending, not yet graded): diagonal ink hatch texture + 2px inset ink border, on the key's existing base color (`--color-paper-bright` for white keys, `--color-ink` for black keys). No fill color from the four interval tokens. No `NoteLabel` shown.
- Revealed/correct (after Check, or during identification's pre-highlighted prompt): full interval-color fill (root/3rd/5th/7th) exactly as lookup/showcase render it, with `NoteLabel` shown. This is the ONLY state that uses the four interval-color tokens on keyboard keys.
- These two states are visually incompatible by construction (hatch-texture-on-base-color vs. solid-interval-fill) so a user can never mistake "I clicked this" for "this is confirmed correct," satisfying constraint 2 directly.
- A key can transition from selected → revealed-correct (on Check, if it was actually part of the answer) or selected → nothing (on Check, if the user's overall answer was wrong and the reveal instead shows only the target's own notes newly highlighted; the user's own selection styling is cleared once feedback renders, since `PlayedVsCorrectDiff`'s text rows carry "what you played" from that point forward, not a lingering hatch state on the keyboard itself).

Focus rings: ink `#221e17`, 2px offset outline — applies identically to keyboard keys (interactive mode), Check/Clear buttons, ChoiceGrid options, and Next button (unchanged rule from Phase 1).

## Copywriting Contract

Tone: warm print-shop-clerk voice per Phase 1 D-01..D-05 (fun, witty, never scolding, occasional French winks, uppercase mono for status lines). **No em dashes anywhere** — periods, colons, commas only. Chord notation hyphens (`C-7`) are unaffected. Mid-dot (`·`) is used as a visual separator in the score register, which is not an em dash and is already an established separator glyph in this app's mono status lines.

| Element | Copy |
|---------|------|
| Page heading | `Drills` |
| Nav link | `Drills` (masthead, per D-13) |
| Construction prompt instruction | `Click the notes for {symbol}.` |
| Identification prompt instruction | `Name this chord.` |
| `Check` button | `Check` |
| `Clear` button | `Clear` |
| `Next` button | `Next` |
| Right-answer confirmation | `Nailed it.` (restraint per Phase 1 D-07, stamp animation is the reward, this is a one-line caption not a celebration banner) |

| Wrong-answer headline | `Not quite.` |
| Wrong-answer headline, alt variants (rotate, avoid immediate repeat) | `Not quite.`, `Close, but no cigar.`, `Not this time.` |
| Wrong-answer teaching lead-in (above the revealed keyboard) | `Here is the shape:` |
| Diff row label: what user played | `You played:` |
| Diff row label: correct answer | `Correct:` |
| Score register format | `{n} RIGHT · {n} STREAK` (uppercase mono, e.g. `7 RIGHT · 3 STREAK`) |

| Empty/loading state | none needed: the loop always has a question ready on page load per 03-CONTEXT's "zero-friction" requirement (no setup screen, no empty state to design) |
| Destructive confirmation | none — `Clear` discards only an in-progress, ungraded selection (not a saved or graded answer), so no confirmation copy is needed; reload discarding the in-memory score similarly needs no confirmation (D-10, ephemeral by design) |

## Layout Contract (new this phase)

Vertical stack, top to bottom, applies to both desktop and mobile portrait (mobile compresses spacing per the above-the-fold exception, same order):

1. Masthead (brand + nav, now including Drills), unchanged from Phase 2
2. Page heading (`Drills`) — Heading role, `md` top margin below masthead
3. `ScoreRegister` — Label-size mono, `xl` margin above the DrillCard
4. `DrillCard`:
   a. `DrillPrompt` (chord glyph + instruction for construction; pre-highlighted keyboard + instruction for identification)
   b. Keyboard (interactive/clickable for construction; already rendered as part of 4a for identification, not duplicated)
   c. Action row: `AnswerActions` (Check/Clear) for construction, or `ChoiceGrid` (4 options) for identification
   d. `FeedbackBanner` (only after an answer is submitted; absent before)
5. `Next` button (only after `FeedbackBanner` renders; advances to a new question, replacing the entire DrillCard content, not navigating away from `/drills`)

On mobile portrait, items 1 through 4c must fit above the fold per the above-the-fold exception (constraint: "keep the primary question-answer-feedback loop above the fold on a phone in portrait"). Item 4d (`FeedbackBanner`) and item 5 (`Next`) may sit below the fold since they only appear after the user has already engaged with the visible question, and scrolling to see feedback/teaching content is an acceptable secondary interaction (unlike the question itself, which must be immediately actionable with no scroll).

Interaction flow (restates 03-CONTEXT D-04/D-05/D-07 as the visual/interaction spec):
- Question type is decided randomly per question (construction or identification, interleaved per D-06); the page does not show both simultaneously and does not expose a mode toggle (no segmented control, per Claude's Discretion default).
- Construction: keys toggle freely (click again to deselect) with no auto-grading; `Check` is the only trigger for grading. `Clear` deselects all without grading or advancing.
- Identification: tapping a `ChoiceGrid` option grades immediately (no separate Check step, since selecting one of 4 discrete options IS the complete answer).
- After grading (either direction), the keyboard's interactive/selectable affordances are disabled (no further clicks change anything) until `Next` is pressed and a new question replaces the card.
- `Next` never auto-fires; the user reads the feedback at their own pace (D-07).

## Implementation Notes for Planner/Executor

- Extend `PianoKeyboard.svelte` with an `interactive` mode rather than forking a new component: add `interactive?: boolean` and an `onToggle?: (letter: string) => void` (or equivalent event) prop, plus internal `selected: Set<string>` state (or lift selection state to the parent page and pass it down, planner's call) that only applies when `interactive` is true. The existing display-only path (Phase 2 lookup, Phase 1 showcase) must render byte-for-byte identical output when `interactive` is omitted/false — add tests asserting this non-regression.
- The selected-key hatch texture can be implemented as a CSS `repeating-linear-gradient` on the key element (no new image assets, consistent with the app's zero-icon-library, hand-rolled-CSS approach) layered under the existing white/black key background color.
- `matchChord`'s pure pitch-class-set comparison (D-01..D-03 from 03-CONTEXT) determines correct/incorrect and the missing/extra diff; this UI-SPEC only constrains how that result is *rendered* (`PlayedVsCorrectDiff`, keyboard reveal), not the matching logic itself, which is a planner/executor concern in `src/lib/drills/matchChord.ts`.
- Distractor generation for `ChoiceGrid` (3 wrong options + 1 correct, shuffled) is a logic concern for planner/executor (per 03-CONTEXT Claude's Discretion: must be plausible, always parseable, never enharmonically identical to the correct answer); this spec only constrains the grid's visual and interaction contract.
- Reuse `formulaFor`, `aliasLine` (from `$lib/lookup/chordPresentation`), `PianoKeyboard`, `ChordGlyph`, `IntervalChip`, `NoteLabel`, `Button` unmodified wherever the contract above calls for them (wrong-answer reveal, ChoiceGrid glyphs, ScoreRegister styling primitives) — do not fork copies.
- No new CSS custom properties are needed in `src/app.css` for color/spacing/typography tokens (everything used here already exists from Phase 1/2). The one net-new visual primitive (the diagonal hatch texture for selected keys) is a component-scoped CSS pattern in `PianoKeyboard.svelte`'s `<style>` block, not a new design token, since it is a state treatment specific to one component rather than a reusable palette/spacing value.
- `+layout.svelte`'s `navLinks` array is the only change needed for D-13; no new masthead visual logic.
