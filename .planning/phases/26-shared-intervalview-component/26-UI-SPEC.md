## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-paper` #f2ecdd | Page background behind the component (inherited, not set by this component) |
| Secondary (30%) | `--color-paper-bright` #faf6ea / 2px `--color-ink` borders | Not introduced by this component — it has no card chrome of its own; it sits directly on the page background like the row it replaces |
| Accent (10%) | The 7 reserved interval-role fills: `--color-root`, `--color-second`, `--color-third`, `--color-fourth`, `--color-fifth`, `--color-sixth`, `--color-seventh` | **Tone chips only** (rendered via `IntervalChip`, keyed by each note's root-relative `role`). This is the app's fixed, reserved interval color language (DESIGN-02) — never repurpose it for anything else in this component. |
| Destructive | n/a | No destructive action exists in this phase (pure display + a non-destructive view toggle) |

**Explicit reservation — accent is used for tone chips ONLY:**
- Gap markers (`+m3`, `+M3`, `+m3`) render in `--color-muted` (#7d7462) plain mono text — never a colored chip, never a role fill. They represent the distance *between* two notes, not a note's own root-relative role, so coloring them with the reserved role palette would misuse DESIGN-02's fixed semantics (a `+m3` gap is not itself "the third of the chord").
- The view toggle (segmented control) reuses the LocaleToggle/BuildSession convention: active segment fills `--color-ink` (never `--color-vermilion` or any reserved interval color), because vermilion/verdigris/etc. are reserved for interval-role semantics and must never be repurposed for chrome (this is a standing house rule, not new to this phase).

## Component Contract (IntervalView.svelte)

This section is the binding design detail beyond the generic template — it resolves every open question CONTEXT.md left at Claude's discretion, so the planner/executor build one shared interpretation.

### Data shape (pure module — `src/lib/lookup/chordPresentation.ts`)

Add a sibling to the existing `formulaFor`:

```ts
export interface StackedGap {
  /** Neutral connective label between two consecutive tones, e.g. "+m3". */
  label: string;
  /** French long name for tooltip/aria, e.g. "tierce mineure". */
  longFr: string;
}

export interface StackedThirds {
  /** Same tones as formulaFor(chord), in order — root-relative label/role/letter/solfege unchanged. */
  tones: FormulaEntry[];
  /** Adjacent-gap intervals between consecutive tones; length = tones.length - 1. */
  gaps: StackedGap[];
}

export function stackedThirdsFor(chord: ChordResult): StackedThirds
```

Implementation notes (pin the algorithm, not just the shape):
- `tones` = `formulaFor(chord)` verbatim (do not recompute) — the stacked view's tone chips read the exact same root-relative degree label (`R`, `♭3`, `5`, `♭7`) as the formula view; only the **display** of the root tone's label differs (see below), and gap markers are interleaved between them.
- `gaps[i]` = `intervalBetween(chord.notes[i].letter, chord.notes[i + 1].letter)`, displayed as `+${info.short}` (e.g. `+m3`), with `longFr` carried through for tooltip/aria use. This is the exact computation `WhyTheseNotes` already performs for consecutive notes — reuse `intervalBetween`, do not add a second interval-naming path.
- Canonical acceptance example (must match exactly): `Cm7` → tones read `root, ♭3, 5, ♭7`; gaps read `+m3, +M3, +m3`. Full stacked rendering: `root +m3 ♭3 +M3 5 +m3 ♭7`.
- Per-quality gap-pattern invariants to cover in unit tests (one fixture per quality, per CONTEXT.md's specifics): maj7 → `M3, m3, M3`; m7 → `m3, M3, m3`; dom7 (7) → `M3, m3, m3`; ø7 (m7b5) → `m3, m3, M3`; °7 (dim7) → `m3, m3, m3`; plus a triad (2 tones, 1 gap) and one extended chord (9/11/13, 5+ tones) for the wrap/layout check.

### Root-tone label resolution (discretion point, now locked)

- **Formula view:** root tone chip label stays `"R"` — this is `formulaFor`'s existing, unchanged output. Formula mode must be byte-identical to the current Lookup row (REG-01).
- **Stacked view:** root tone chip label displays as the word `"root"` (lowercase, matching the design doc's own literal example `root +m3 ♭3 …`), NOT `"R"`. This is a display-only override in the component (or a `displayLabel` computed at render time) — it does not change `FormulaEntry.label`, `stackedThirdsFor`'s data, or anything `formulaFor`'s consumers rely on.

### View toggle — exact affordance

Reuse the existing segmented-toggle pattern verbatim (`LocaleToggle.svelte` is the structural precedent, cited directly in CONTEXT.md):

- `<div role="group" aria-label={t('interval-view.aria.group')}>` wrapping two `Button` instances.
- Segment 1 "Stacked" (default `aria-pressed="true"`), Segment 2 "Formula".
- `variant="primary"` on the active segment, `variant="ghost"` on the inactive one, exactly like `LocaleToggle`.
- Active-segment fill overridden to `--color-ink` (not `Button`'s default vermilion) via the same scoped `:global(.ps-button[aria-pressed='true'])` CSS override `LocaleToggle` already uses — vermilion/verdigris/etc. stay reserved for interval semantics, never chrome.
- Toggle state is local `$state` inside `IntervalView`, defaulting to `'stacked'`. No persistence (explicitly out of scope per CONTEXT.md's Deferred Ideas — no schema change this milestone).
- Toggle sits directly above the tone row, `margin-top: var(--spacing-md)` from the piano keyboard/inspect elements above it (matches the current row's `mt-6` = 24px... actually reuse the current block's existing `mt-6` wrapper spacing unchanged; the toggle is a new first child inside that same wrapper, so the wrapper's own outer margin does not change).

### Gap markers vs. tone chips — the visual distinction that must never blur

| | Tone chip | Gap marker |
|---|---|---|
| Component | `IntervalChip` (reused, unchanged) | Plain `<span>`, no chip styling |
| Color | Filled with the reserved role color (`--color-root`/`--color-third`/etc.) + matching on-fill text color | `--color-muted` text on transparent background, no border, no fill |
| Border | 2px `--color-ink` (via `IntervalChip`'s existing CSS) | none |
| Font | `--font-mono`, 12px, 700 weight (via `IntervalChip`) | `--font-mono`, 12px, 700 weight (same type role, different color/chrome — so it reads as "same family, different kind of thing," not a jarring mismatch) |
| Tap target | Yes — 44×44px minimum, wrapped in a button (see Interaction Contract) | No — not interactive, no button wrapper, no minimum size |
| Represents | A chord tone's root-relative role (semantic, reserved) | The distance between two adjacent tones (structural, neutral) |

This distinction is the core visual contract of the phase: a beginner must be able to tell at a glance "this colored box is a note I play" vs. "this gray text between two boxes is how far apart they are."

### Layout

- Single horizontal row, `display: flex; flex-wrap: wrap; align-items: flex-end; gap: var(--spacing-sm);` — matches the current formula row's `flex gap-4` closely enough that wrap behavior at phone width (390px) is unchanged; adjust the exact gap token only if extended-chord fixtures (9/11/13, 5+ tones) overflow at 390px, in which case drop to `--spacing-xs` between gap-marker/chip pairs rather than changing the wrap strategy.
- Each **tone** renders as a column: chip on top, letter below, solfège below that (`flex-direction: column; align-items: center; gap: var(--spacing-xs)`) — identical structure to the current `.formula-tap` column.
- Each **gap marker** renders as a single inline span, vertically centered against the chip row (`align-self: center`), with no letter/solfège lines beneath it (it names a distance, not a tone).
- In **formula mode**, gap markers are absent entirely — it renders exactly the tone-chip columns in a row, byte-identical to today (`R, ♭3, 5, ♭7` reads as chip, chip, chip, chip with no interstitial markers).
- Stays inline in normal page flow always — never fixed/docked, per the house "keyboards/rows render inline" rule (`keyboard-inline-not-docked` memory). Confirmed phone-friendly by construction (reuses the exact wrap/flex approach already proven at 390px by the row it replaces).

### Interaction contract — tap-a-tone-to-inspect (REG-01 critical)

- **Formula mode:** reproduce the current behavior exactly. Each tone chip is wrapped in a `button.formula-tap` (same class, same 44×44 min-size CSS, same `aria-label={`Inspect ${entry.letter}`}`), calling the passed-through inspect handler on click. This is a direct lift of the existing `{#each formulaFor(result) as entry}` block into the component — no behavior change, just relocation.
- **Stacked mode:** tone chips are **also** tap-to-inspect, for parity (CONTEXT.md's explicit default: "YES for parity, since each chip still maps to a real chord tone"). Same `button.formula-tap` wrapper, same handler, keyed off the same `entry` (from `stackedThirdsFor(chord).tones`, which is `formulaFor(chord)` under the hood) — so a single shared inspect-handling code path serves both modes; the component does not need two different click handlers.
- **Gap markers are never tappable** in either mode — no button wrapper, no `onclick`, no `aria-label`, no `role="button"`. They are decorative/informational text. Mark them `aria-hidden="true"` if rendered as a bare `<span>` between two focusable buttons, so screen-reader users tab between the two tone buttons without an unlabelled stop in between (each tone's own chip already carries `title`/`aria-label` via `IntervalChip`'s `longName` prop, so the interval-to-root and adjacent-gap information is still available via the chips themselves and via any tooltip surfaced on the gap span, but never as a distinct focus stop).
- Component API: `Props { chord: ChordResult; onInspectTone?: (entry: FormulaEntry) => void }`. When `onInspectTone` is omitted, render the same markup with inert (non-button, plain) chips — mirrors the codebase's existing "gated prop, byte-identical when omitted" convention (see `IntervalChip.longName` precedent) so a future Learn-hub embedding (Phase 28) that has no inspect handler yet doesn't need special-casing.

### Dual naming (letters primary, solfège secondary)

- Unchanged from the current row: each tone column shows letter first, solfège second, both as separate `text-label font-mono` lines.
- Solfège carries its accidental through (`E♭` renders as `Mi♭`) via the already-fixed `letterToSolfege`/`note.solfege` pipeline (per the related-work fix landed this session) — IntervalView does not re-derive solfège, it reads `entry.solfege` off the shared `FormulaEntry`/tone data verbatim.
- This dual-naming rule applies identically in both stacked and formula modes (gap markers carry no letter/solfège — they are not tones).

### Test-ID / DOM-parity contract (for REG-01 and the planner's test plan)

- Outer wrapper: `data-testid="interval-view"` with `data-view="stacked"|"formula"` reflecting the active toggle state (lets tests target the active mode without relying on visual order).
- Formula-mode inner content keeps the existing `data-testid="interval-formula"` on its row (or an equivalent selector) so any existing test asserting on that testid continues to pass unmodified once `+page.svelte`'s inline block is replaced by `<IntervalView>` — the component's formula-mode render tree must be a drop-in, not just visually equivalent.
- New stacked-mode row: `data-testid="interval-stacked"`.
- Toggle: `data-testid="interval-view-toggle"`, with each segment individually queryable by its `aria-pressed` state (standard house pattern, same as `LocaleToggle`/`SongFilterToggle` tests already do).
