# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Mode:** Autonomous overnight run. No `11-RESEARCH.md` exists (not required for this phase); `11-CONTEXT.md` is the authoritative upstream source and already resolved every scheduling/data-model question (D-01..D-11). This document resolves the remaining VISUAL questions the same way CONTEXT.md resolved the engineering ones: by grounding in the existing Print Shop system (`src/app.css`, Phases 1-10's shipped components) rather than inventing anything new. Every discretionary call below is marked **(Autonomous decision)** with its rationale, so it can be challenged on read-back rather than silently assumed.

**Phase scope:** A new `/recall` surface: a due-today reveal-then-grade session (MEM-01/02/03) and a fact × mode recall map (MEM-04). Reuses every existing token and component; introduces zero new colors, zero new spacing values, zero new type sizes. This is also the app's first real use of the FSRS scheduler and Dexie/IndexedDB (D-08) — a brand-new engine, but a deliberately unremarkable UI on top of it.

**Sources:** `11-CONTEXT.md` (D-01..D-11, locked), `.planning/PROJECT.md` (no em dashes, shop voice, local-first), `src/app.css` (token contract, locked), `.claude/skills/spike-findings-music-learn/references/memorization-engine.md` (spikes 006/009), `.claude/skills/sketch-findings-music-learn/references/drill-feedback.md` (legend + wrong-fill convention), `src/routes/scales/+page.svelte` + `ScaleKeyboardDrill.svelte` (mode-toggle-card structure, register-line convention, completion-card convention — most recent shipped phase, followed as the closest structural precedent), `src/routes/drills/+page.svelte` (reveal-then-feedback flow, choice-grid button pattern, score-register convention), `src/routes/progress/+page.svelte` (page-state machine convention: loading/empty/error/populated), `src/lib/components/{Button,ChordGlyph,IntervalChip,NoteLabel,PianoKeyboard}.svelte` (components reused verbatim, no API changes needed), `.planning/phases/10-scale-keyboard-drill/10-UI-SPEC.md` (structural/documentation precedent for this file).

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f2ecdd` (paper) | Page background — unchanged |
| Secondary (30%) | `#faf6ea` (bright paper) + `#221e17` (ink) | Card surface, borders, all text — unchanged |
| Accent (10%) | `#c8502e` (vermilion) | See reserved-for list below — unchanged budget, no new usage pattern this phase |
| Destructive | none this phase | No destructive actions exist in this drill (see Copywriting Contract) |

Accent (vermilion) reserved for — unchanged from every prior phase, no new entry added:
1. Primary button background (`Show Answer`, same primary `Button` variant already defined; `Practice Now` links reused verbatim from Progress)
2. Root interval-color token (unchanged usage — appears only inside a `chord-formula` reveal's formula chips / display-mode keyboard, exactly as Drills already renders it)

**Never** use vermilion, or any of the seven interval-role tokens (root/second/third/fourth/fifth/sixth/seventh), for: grade-button distinction, recall-map cell states, or any new semantic this phase introduces. This is the one hard rule this UI-SPEC adds: **the interval-color language is app-wide and fixed (DESIGN-02); every named hue in `src/app.css` is already claimed by a chord/scale-degree role. Phase 11 introduces two brand-new semantics (grade urgency, mastery state) and must encode both WITHOUT touching hue** — texture (ink hatch), fill density (solid ink vs. outline), and the existing achromatic `--color-wrong` gray are the only vocabulary available, mirroring how `PianoKeyboard`'s existing `--selected` state already solved this exact problem with a diagonal ink-hatch instead of a new color.

### Grade-button treatment (new this phase, no new tokens)

| Button | Background | Text | Rationale |
|--------|-----------|------|-----------|
| Again | `--color-wrong` (`#b8b0a0`) | `--color-ink` | Reuses the app's existing "you got this wrong" gray verbatim — semantically exact (Again = you didn't recall it), not a new color |
| Hard | `--color-paper-bright` + ink border (ghost variant) | `--color-ink` | Plain ghost, unchanged |
| Good | `--color-paper-bright` + ink border (ghost variant) | `--color-ink` | Plain ghost, unchanged — deliberately NOT accented. Anki-style apps often highlight the "default" rating, but doing so here would require a hue outside the fixed interval language. Distinguish by label text alone. |
| Easy | `--color-paper-bright` + ink border (ghost variant) | `--color-ink` | Plain ghost, unchanged |

### Recall-map cell states (new this phase, no new tokens — texture/fill only)

| State | Treatment | Meaning |
|-------|-----------|---------|
| Not yet seen | `--color-paper` fill, 1.5px `--color-faint` border, no mark | Card doesn't exist yet for this (fact, mode) pair |
| Due | `--color-paper-bright` fill + diagonal ink-hatch (identical `repeating-linear-gradient` recipe `PianoKeyboard`'s `.piano-keyboard__key--selected` already uses, at the same 12% ink opacity) + inset 2px ink border | Card exists, `due <= now` |
| Weak | Solid `--color-wrong` fill + a small `!` glyph (ink, Label-role, centered) | Card exists, recent lapse (state was `Review`, most recent grade was `Again`) — reuses the existing wrong-gray token, same reasoning as the Again button |
| Mastered | Solid `--color-ink` fill + a small `✓` glyph in `--color-paper-bright` | Card exists, `state === 'Review'` and not currently due and no recent lapse — "fully inked," the letterpress metaphor for "this one's set" |

### Day-interval label format (grade-button tag; applies to all four buttons)

Exact formatting rule (deterministic, no ambiguity for the executor):

```
days < 14   → "{round(days)}d"     e.g. "1d", "3d", "8d", "13d"
14 ≤ days < 60 → "{round(days/7)}w"   e.g. "2w", "8w"
days ≥ 60   → "{round(days/30)}mo"   e.g. "2mo", "19mo"
```

This mirrors the fixed FSRS intervals from CONTEXT.md D-02/D-03 (New+Again=1d, Hard=2d, Good=3d, Easy=8d; a Good chain grows 3→14→57→196→586d) — everything through "Easy" on a first review stays in the `d` band; only a mature card's Good/Easy tags roll into `w`/`mo`. Computed via `scheduler.repeat(card, now)` (D-04, preview only, no commit) on every card load, so all four tags are visible before any grade is chosen.

## Layout Contract (new this phase)

### `/recall` page structure

1. `<h1>Recall</h1>` (Heading role, matches every other page's h1 treatment)
2. Intro line (Body role)
3. Mode toggle row (`Review` / `Map`), `xl` gap below the intro line — same Button-group markup as `/scales`' Explore/Practice toggle
4. Bordered card (`border-ink bg-paper-bright border-2 p-6`, same shared card convention every page uses) containing whichever mode is active

### `Review` mode, inside the card

Vertical stack, single column at every breakpoint (no bespoke landscape two-pane split like Drills — the reveal content here is lighter: no dual-keyboard input surface to make room for):

1. Register line (Label role, mono, `aria-live="polite"`, matches `ScaleKeyboardDrill`'s `register` line exactly in role/markup)
2. Prompt block: identity line + question line (per fact-kind table above)
3. `Show Answer` button (primary), centered, generous top margin (`md`) — the only interactive element until tapped
4. On tap: reveal callout + reveal content appear below (per fact-kind table), with the existing `.stamp` keyframe (240ms, `prefers-reduced-motion`-guarded, already in `app.css`) firing on entry — reused verbatim, no new animation
5. Grade-button row (`Again`/`Hard`/`Good`/`Easy`, `grid grid-cols-2 gap-2 sm:grid-cols-4`, same grid shape as Drills' existing choice-grid), `md` gap below the reveal content

Interaction flow (restates MEM-01/02/03 as the visual/interaction spec):
- The session begins the instant `Review` mode is entered — no separate "Start Session" click, same zero-friction rule every drill surface in this app already follows (Drills, `ScaleKeyboardDrill` both go interactive immediately on entering their mode/tab).
- **(Autonomous decision)** Tapping any grade button both commits the FSRS rating AND advances to the next queued card in one action — no separate "Next" click. Rationale: unlike Drills (where feedback needs a beat to read before moving on), a grade button here IS the user's considered response after already reading the full reveal; requiring a second tap to advance would be pure friction with no payoff, and this matches the project's established "tapping a choice IS the complete answer" precedent (Drills' identification questions, D-05-style).
- `Again`-graded cards are re-enqueued later in the same session (D-10, Anki-style second look) — the register's `{n} LEFT TODAY` count reflects this (an `Again` tap does not decrement `n` below its pre-re-enqueue value).
- Reaching an empty queue shows the session-complete card, replacing items 1-5 in place (mirrors `ScaleKeyboardDrill`'s in-place completion swap, not a separate route).
- No skip/pass-without-grading action exists — every due card must be graded to leave the queue, by design (this is the entire mechanism, not an obstacle to route around).

### `Map` mode, inside the card

1. Kind filter tabs (`All`/`Chords`/`Intervals`/`Scales`), `md` gap below the card's top
2. Grid: CSS grid, one row per fact (filtered by the active kind tab), one column per mode (currently just `Formula`, see Implementation Notes). Row label: fact identity at Heading-role weight (chord symbols in `font-serif font-bold`, matching `ChordGlyph`'s family without invoking its full misregistered-shadow display treatment; interval/scale-degree facts in `font-mono font-bold` to match their existing treatment elsewhere)
3. Legend row beneath the grid (four swatches, per Color section above)

### 5-state page machine (Review mode)

Mirrors the Progress page's `PageState` convention exactly (`loading | empty | error | populated`), extended with the session's own terminal state:

| State | Trigger | Renders |
|-------|---------|---------|
| `loading` | Dexie not yet opened/queried | `Label` line `COUNTING TODAY'S CARDS...` (same mono-uppercase convention as Progress's `FETCHING THE LEDGER...`), no skeleton needed (this is a near-instant local read, unlike Progress's network fetch) |
| `empty-no-deck` | Deck query returns zero cards total (first-ever visit, defensive) | Empty-state-1 copy above |
| `empty-none-due` | Deck has cards but none `due <= now` | Empty-state-2 copy above |
| `reviewing` | At least one card due | The prompt/reveal/grade flow above |
| `complete` | Queue was non-empty, now empty | Session-complete card |
| `error` | Dexie open/read threw | Error-state copy above |

## Implementation Notes for Planner/Executor

- **Nav insertion:** add `{ href: '/recall', label: 'Recall' }` to `navLinks` in `src/routes/+layout.svelte`, positioned between `Drills` and `Scales` (see Design System table above).
- **This is the app's first Dexie/IndexedDB consumer.** No existing persistence pattern to mirror 1:1 — follow CONTEXT.md D-08/D-09 (schema-versioned, Zod `.coerce.date()` at every read boundary) exactly; this UI-SPEC only fixes the visual outcome, not the storage shape.
- **Grade-button interval preview (D-04):** call `scheduler.repeat(card, now)` (no commit) on every card render to populate all four tags before any button is tapped — never compute a tag lazily on click, or the labels would be wrong/stale the instant the user needs them.
- **Recall-map grid shape:** Phase 11 ships exactly one mode column (`Formula`). Build the grid as a genuine N-column CSS grid (not a hardcoded 1-column special case) so Phase 13's `see-play`/`hear-name`/`notes-symbol` columns can be added later without a redesign — this is the one piece of forward-looking structure this UI-SPEC asks for, and it costs nothing now (an N=1 grid renders identically to a fixed 1-column layout).
- **Mastery-state derivation** (which of the 4 cell states a card is in) is a data-layer question already answered by CONTEXT.md D-11 ("derive cell state from card.state + due date + recent lapses") — this UI-SPEC only fixes the 4 states' visual encoding (texture/fill, never hue) and their exact copy/glyphs.
- **`--color-wrong` dual duty:** this phase reuses `--color-wrong` for both the `Again` grade button and the recall-map `Weak` cell. Both usages are semantically "you got/get this wrong" — no new token needed, and this is consistent with the token's existing name and Sketch 001 origin (it was never scoped to "wrong-answer keyboard fill only").
- **Ink-hatch reuse:** the `Due` cell's diagonal hatch should literally reuse `PianoKeyboard`'s `.piano-keyboard__key--selected` `repeating-linear-gradient` recipe (same angle, same 12% ink opacity, same 7px repeat) rather than inventing a new pattern — copy the CSS custom-property-based gradient, not just the visual idea, so any future palette tweak to that gradient (opacity, angle) only needs to change in one place philosophically even though it's duplicated per-component (no shared CSS class exists across these two unrelated components today; extracting one is optional polish, not required by this UI-SPEC).
- **Chroma-grading callout (defers to Phase 13, not built here):** CONTEXT.md's "grade by chroma/MIDI never letters" constraint applies to played-note recall modes (`see-play`, `notes-symbol`) which are Phase 13 scope. Phase 11's reveal-then-self-grade flow has no played-note input at all (the user grades their OWN recall honestly, there's nothing to compare against a keyboard tap), so this constraint has no surface in this phase's UI — noted here only so it isn't mistakenly "implemented" against the wrong feature.
- **No audio changes needed:** the reveal step MAY optionally play the revealed chord/interval/note via the existing `playChord`/`playNote` (`$lib/audio/audio`) the same way Drills' reveal always does — recommended for consistency but not load-bearing for MEM-01..04; planner's call whether to wire it in this phase or leave it to Phase 13's fuller multi-modal audio work.
- **Session-complete "View Recall Map" secondary CTA** only makes sense once `RecallMap` exists in the same component tree (both tabs live under one `/recall/+page.svelte`, mirroring `/scales`) — do not build it as a separate route/navigation.
