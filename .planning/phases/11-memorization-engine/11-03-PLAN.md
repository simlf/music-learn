<objective>
Create the Dexie/IndexedDB persistence layer for FSRS cards: `src/lib/srs/deck.ts`, storing one record per (factId, mode) with a Zod schema that coerces `due`/`last_review` back into real `Date` instances on every read (CONTEXT.md D-09's "critical trap" — these fields silently become strings through storage round-trips and comparisons against them fail silently, never throwing). This is the app's first Dexie/IndexedDB consumer (per 11-UI-SPEC.md).

Purpose: this module is the single gateway between the scheduler (11-01) and every UI surface (11-05 RecallSession, 11-06 RecallMap) — due-card queries (MEM-01), grade persistence (MEM-03), and recall-map cell-state derivation (MEM-04) all go through it. Getting the Date-rehydration boundary right here, once, protects every later plan from re-introducing the silent-no-throw bug D-09 warns about.

New cards are introduced gradually (a documented discretionary design, not a CONTEXT.md-literal requirement): the 11-UI-SPEC.md's empty-state copy ("Play a few Drills first. Recall cards show up here as you meet new chords, intervals, and scale degrees") and its recall-map "Not yet seen" cell state both presuppose a deck that starts genuinely empty and fills in over time, not one pre-seeded with all 192 facts on first load (which would also dump 192 immediately-due cards on the very first session — an overwhelm problem the blueprint's own "stagger... overwhelm" language warns against for modes, generalized here to raw card introduction). `introduceNewCards` throttles this to a small batch per call.
Output: `src/lib/srs/deck.ts` and its passing test file, plus `dexie@4.4.4` and `zod@4.4.3` added to package.json dependencies and `fake-indexeddb@6.2.5` added to devDependencies.
</objective>
