Create `src/lib/midi/webmidi.ts` as the single boundary between this app and the `webmidi` package. Structure it on `src/lib/audio/micInput.ts`, which solves the identical problem for the microphone.

Header comment: adapt micInput.ts's contract statement. State that every state-machine decision lives in `midi.svelte.ts` and this module's only job is wiring enable / inputs / port events; that merely importing this module touches no browser API because every `navigator` / `window` / package reference lives inside a function body; and that the package itself is reached through a lazy dynamic import so the adapter-static prerender (strict mode, run under Node where `navigator` does not exist) can never execute it, and so the library stays out of the initial client bundle for the many browsers that will never use it.

Exported types:
- `MidiUnsupportedReason` = the union `'no-window' | 'unsupported'`.
- `MidiConnectFailure` = the union `'unsupported' | 'permission-denied' | 'unknown'`.
- `MidiInputInfo` = interface with `id: string`, `name: string`, `manufacturer: string`. This is the app's own flat DTO; raw package port objects must not leak through `enableMidi`'s result.
- `MidiPortKind` = the union `'input' | 'output'`.
- `MidiPortEvent` = interface with `type: 'connected' | 'disconnected'`, `portKind: MidiPortKind`, `id: string`, `name: string`.
- `MidiEnableResult` = the union `{ ok: true; inputs: MidiInputInfo[] } | { ok: false; reason: MidiConnectFailure }`.

Exported functions:
- `midiUnsupportedReason(): MidiUnsupportedReason | null` mirroring `micUnavailableReason()`'s guard ladder exactly: return `'no-window'` when `typeof window === 'undefined' || typeof navigator === 'undefined'`; return `'unsupported'` when `typeof navigator.requestMIDIAccess !== 'function'`; otherwise return `null`. Web MIDI needs no secure-context or constructor check beyond that, so the ladder is two rungs, not four.
- `isMidiSupported(): boolean` returning `midiUnsupportedReason() === null`, mirroring `isMicAvailable()`.
- `mapEnableError(err: unknown): MidiConnectFailure` mirroring `mapGetUserMediaError()`: read the error name (`DOMException` name, else `Error` name, else empty string); map `SecurityError` and `NotAllowedError` to `'permission-denied'`, `NotSupportedError` to `'unsupported'`; then, as a fallback, map any error whose lowercased message contains the word permission to `'permission-denied'` (webmidi can wrap the underlying DOMException in a plain Error, so the name alone is not always available); otherwise `'unknown'`.
- `enableMidi(): Promise<MidiEnableResult>` which guards on `midiUnsupportedReason()` first and returns `{ ok: false, reason: 'unsupported' }` before touching anything (same guard-first ordering as `startMicSession`), then lazily loads the package namespace, then awaits the package's `enable` call passing exactly one options object `{ sysex: false }`. The app has no system-exclusive use case (MIDI-02 and MIDI-03 are note-level only), and requesting it would be asking for a broader capability than needed: pass the option explicitly rather than relying on a library default. Wrap the await in try/catch and convert any rejection through `mapEnableError`. On success, map the package's input port list into `MidiInputInfo[]` (id, name, manufacturer only, coercing a missing name or manufacturer to an empty string) and cache the loaded namespace at module scope so `watchPorts` and `activeInput` can reuse it.
- `watchPorts(handler: (event: MidiPortEvent) => void): () => void` which registers one `connected` and one `disconnected` listener on the cached namespace, translating each incoming event's `port` into a `MidiPortEvent` (id, name coerced to a string, `portKind` from the port's own `type` field, and the matching `type`). Before registering, remove any pair this module previously registered, tracked in a module-scope pair of handler references: double registration must be structurally impossible, because the app never calls the package's global disable and a re-registered listener would otherwise fire the same hot-plug twice. Return a disposer that removes both listeners and clears the module-scope references. If the namespace has not been loaded yet, return a no-op disposer without registering anything.
- `activeInput(id: string): Input | null`, typed with a top-of-file `import type { Input } from 'webmidi'` (type-only, erased at build, so it cannot break the prerender). Return the cached namespace's input whose id matches, else `null`; return `null` when the namespace is not loaded. Document this as the Phase 39 seam: Phase 39 attaches note-on and note-off listeners to this Input, and Phase 38 never reads a single note event.

Device presence is discovered exclusively through the two port events above. Nothing in this module may schedule repeated work to re-check the port list: no repeating timer, no delayed re-check, no animation-frame loop. That is MIDI-01's explicit "no polling" constraint and it is grep-asserted below.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| USB MIDI hardware to browser | Device-supplied USB descriptor strings (`name`, `manufacturer`) and port ids cross into the app. A hub, a generic adapter, or a spoofed virtual MIDI port can report any string. Untrusted data. |
| browser permission layer to app | `navigator.requestMIDIAccess` is a permission-gated, fingerprintable capability (the reason Safari refuses to ship it). The app decides when that prompt is surfaced. |
| npm registry to build | `webmidi` package contents enter the build and the shipped client bundle. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-38-01 | Elevation of Privilege | `enableMidi()` in `src/lib/midi/webmidi.ts` | medium | mitigate | Always pass the options object `{ sysex: false }` explicitly to the package's enable call. The app has no system-exclusive use case, and system-exclusive access would allow firmware-level messages to the instrument. Verified by a unit assertion that deep-equals the captured options. |
| T-38-02 | Information Disclosure | `enableMidi()` guard ordering | medium | mitigate | `enableMidi()` returns `{ ok: false, reason: 'unsupported' }` from the feature-detection guard before any package load or API call, so no permission prompt (and therefore no device-enumeration fingerprinting surface) can be reached on an unsupported environment. The gesture gate itself is enforced in plans 38-02 and 38-03. |
| T-38-03 | Denial of Service | `watchPorts()` listener registration | low | mitigate | The module tracks its own registered handler pair and removes the previous pair before registering a new one, so repeated calls cannot accumulate duplicate hot-plug handlers that would multiply state writes on a flapping device. |
| T-38-04 | Tampering | raw port objects escaping the boundary | low | mitigate | `enableMidi()` returns only the flat `MidiInputInfo` DTO (id, name, manufacturer). Raw library port objects are reachable solely through the explicit `activeInput(id)` seam, so no consumer accidentally depends on library internals. |
| T-38-SC | Tampering | npm install of `webmidi` | high | mitigate | 38-RESEARCH.md's Package Legitimacy Audit ran the package-legitimacy gate and returned verdict **OK** (published 2026-03-31, `github.com/djipco/webmidi`, ~19k weekly downloads, zero runtime deps, no postinstall script, Apache-2.0), with no `[ASSUMED]`, `[SUS]`, or `[SLOP]` findings. Pinned exactly at 3.1.16 with the lockfile committed; `npm ls webmidi` asserted in Task 1. No blocking human checkpoint is warranted because no package in this phase is `[ASSUMED]` or `[SUS]`. |
