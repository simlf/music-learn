<objective>
Build the reactive session-wide MIDI connection state: a `.svelte.ts` module holding the state machine, two pure transition functions, a feature-detect-only initializer, and a gesture-gated connect that wires plan 38-01's port events into the state.

Purpose: MIDI-01 requires a live connection state with three distinguishable outcomes (device detected, device disconnected, browser unsupported) driven by device events with no polling, plus hot-plug in both directions with no reload. Putting the state machine in one reactive module (the same idiom `swUpdate.svelte.ts`, `locale.svelte.ts`, and `dueBadge.svelte.ts` already use three times) is what lets a single masthead component render it and Phase 39 consume the same connected device with no second connection layer.
Output: `src/lib/midi/midi.svelte.ts` plus its unit test.

Create `src/lib/midi/midi.svelte.ts`. The `.svelte.ts` extension is mandatory, not cosmetic: a plain `.ts` file's module-level `$state` is not reactive across consumers in Svelte 5. Write a header comment saying exactly that and naming `swUpdate.svelte.ts` / `locale.svelte.ts` / `dueBadge.svelte.ts` as the three existing instances of the idiom.

Export the discriminated union `MidiConnectionState`, keyed on `kind`, with these eight variants and no others:
- `{ kind: 'unsupported' }`: Web MIDI absent (Safari, every iOS browser). The module's initial value, so the prerender is deterministic and MIDI-04 holds before any client code runs.
- `{ kind: 'idle' }`: supported, never asked. The only state that offers a connect affordance.
- `{ kind: 'enabling' }`: a connect attempt is in flight, including the time a native permission dialog is open. Mandatory as of the Chrome 124 permission change: every MIDI access is prompt-gated now, not only system-exclusive access, so a connect click can visibly wait.
- `{ kind: 'connected'; deviceId: string; deviceName: string }`: a device is attached. `deviceId` on the variant (rather than a separate module variable) is what keeps the reducer pure and makes `connectedDeviceId()` a derivation instead of extra mutable state.
- `{ kind: 'no-device' }`: supported and granted, zero input ports ever seen.
- `{ kind: 'disconnected' }`: was connected, now is not. Deliberately distinct from `no-device`; MIDI-01 wants both phrased distinctly. Carries no device name: the ROADMAP asks only that unplugging reads as disconnected.
- `{ kind: 'denied' }`: permission refused.
- `{ kind: 'error' }`: anything else.

Export the two pure functions (no `$state` access inside either, so both are testable with no reactivity and no browser, mirroring `computeUpdateReady`):
- `stateFromEnable(result: MidiEnableResult): MidiConnectionState` mapping plan 38-01's enable result onto the union per the behavior block. The first input in the list wins.
- `nextMidiState(current: MidiConnectionState, event: MidiPortEvent): MidiConnectionState` applying, in this order: (1) if `current.kind === 'unsupported'`, return `current` unchanged; (2) if `event.portKind !== 'input'`, return `current` unchanged; (3) on `connected`, return a `connected` state built from the event's id and name; (4) on `disconnected`, return `{ kind: 'disconnected' }` only when `current.kind === 'connected'`, otherwise return `current` unchanged. Return the identical `current` reference (not a copy) on every no-change path, so a test can assert reference equality and so a reactive consumer does not re-render for a no-op.

Add the reducer-ordering rationale as a comment: guard 1 is the mechanical guarantee behind MIDI-04, and guard 4's `connected`-only condition is what keeps "never saw a device" and "was connected, now is not" from collapsing into one indistinguishable reading.

Then write `src/lib/midi/midi.test.ts` covering the behavior block, following `swUpdate.test.ts`'s file shape and header-comment convention (state plainly that the real device event wiring is not jsdom-testable and is covered by `tests/e2e/midi.spec.ts` plus the hardware UAT in plan 38-04).

| Boundary | Description |

| webmidi port events to app state | `MidiPortEvent` fields (`id`, `name`) originate in the hardware's USB descriptor and pass through this module into the reactive state a component will render. Untrusted data in transit. |
