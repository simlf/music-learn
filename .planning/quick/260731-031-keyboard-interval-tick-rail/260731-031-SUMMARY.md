## How the geometry works

Positions come from the SAME `noteAssignment` map the keys render from, never a second
letter-to-key lookup, so a flat-spelled note, an exotic enharmonic (assignNotesToKeys'
chroma fallback), and a D-02-wrapped note all resolve to the key that actually rendered.
A black key's x-center collapses to exactly `(afterWhiteIndex + 1) * whiteKeyWidthPct`
(its `leftPct` is that minus half its own width). Everything is percentage-based, so the
rail tracks the board at every container width including the scrolling min-width case;
px only enters for the narrow-label threshold.

Gaps are dropped individually when an endpoint is unplaced or when the second endpoint does
not sit to the RIGHT of the first — the one-octave wrap case, where a drawn line would run
backwards and name a distance the board is not showing.

## Deviation from the mockup: square ticks

The mockup's ticks are circles (`border-radius: 50%`). `app.css` carries
`* { border-radius: 0 !important }` as its one absolute rule and NO element in `src/` has
ever exempted itself from it (verified by grep). The handoff anticipated the collision and
named the fallback: "otherwise reconsider circular ticks against the sharp-corner rule."
Ticks ship as 8px squares, which also read as printers' register marks. This is the one
design decision worth a second look from design.

## Verification

- `components.test.ts` (+6 tests) and `chordPresentation.test.ts` (+4 tests): 143 passing.
  Coverage: label text/order, tick counts, quality classes, black-key endpoint geometry,
  non-third dashed treatment, narrow-label drop, rail DOM position + aria-hidden, the
  under-two-notes guard, and non-regression when the prop is omitted.
- `npm run check`: 1473 files, 0 errors, 0 warnings.
- Live Chromium at 1280px and 375px on `/` with C7sus4 (the handoff's own stress chord —
  a P4, a narrow M2, and a m3 ending on the B♭ black key):
  - Line endpoints are pixel-exact against the key centers (C 73 → F 316 → G 397 →
    B♭ 518, the last being a BLACK key's center).
  - Rail width tracks board width exactly (both 660px at phone width, both 1216px at
    desktop); `pointer-events: none` confirmed computed.
  - The M2's label flips to 9px at phone width and back to 11px at desktop, i.e. the
    threshold reacts to real measured key widths, not a fixed assumption.
  - No console errors.

## Known gaps

- The stacked (two-row phone board) suppression path is guarded in code but not exercised
  live: the only surface that opts in (lookup) self-measures its span and therefore never
  stacks. It would only be reachable if a caller passes `octaves={2}` AND
  `showIntervalTicks` on a phone.
- The full `vitest run` shows ~46 failures concentrated in timeouts (25 x "Test timed out
  in 5000ms"). Pre-existing load flakiness, not this change: every failing file passes in
  isolation both with and without these commits (checked on a stashed tree).
- `IntervalView`'s stacked-thirds row and `IntervalScaffold`'s formula strip were left in
  place. The handoff describes moving the information onto the keyboard but does not ask
  for their removal; whether the lookup page now shows the same gaps twice is a design
  call, not an implementation one.
