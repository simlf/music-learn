<investigation_findings>
Read this before touching anything. It answers the correctness question the task brief
flagged, and it reverses a decision the previous quick task LOCKED.

**A one-octave board genuinely cannot express most construction targets.**
`buildConstruction` derives each target's MIDI from `toAscendingPitches`, which ascends from
octave 4. `PianoKeyboard`'s `octaveForWhiteIndex` is `BASE_OCTAVE + floor(index / 7)`, so a
one-octave span is white indices 0..7 = **C4 through C5, MIDI 60..72 inclusive** (all 13
keys). Two octaves is C4..C6, MIDI 60..84.

Worked cases against MIDI 72:

| Target | Step MIDIs | Fits C4-C5? |
|--------|-----------|-------------|
| Cm7 | 60, 63, 67, 70 | yes |
| Dm7 | 62, 65, 69, 72 | yes (exactly) |
| Em7 | 64, 67, 71, **74** | no |
| A major triad | 69, **73**, **76** | no |
| B major scale | 71 .. **83** | no |

The seeded Playwright build-it deck (`helpers.ts` RECIPES) is triads C D E F G A, so the
A triad alone already produces an unreachable target. Without a grading change, a
one-octave board would make those steps **impossible to complete** (every tap of the right
pitch class grades `wrong-octave` forever).

**Therefore the span change REQUIRES a grading change.** The chosen answer is octave
folding, driven by an explicit board-top MIDI:

- Fold the target down whole octaves until it sits at or below the board's top key.
- Grade a tap correct when it matches the target's own MIDI **or** the folded MIDI.
- Keep `wrong-octave` for a chroma match that is neither: on a one-octave board that is
  still reachable for the duplicated C (C4 vs C5) and for every target already inside
  C4-C5, so the "you're stacking upward" teaching survives exactly where it is meaningful
  and is dropped only where it is physically unexpressable.
- Compute `wrong-pitch-class` semitones/direction against the **folded** target, so the
  diagnostic reads "7 half steps too low", not "19".
- With no board-top supplied (or a two-octave board, whose 84 ceiling is above every
  target this app produces: the highest is B major's B5 = 83) folding is a no-op and every
  existing behavior is byte-identical.

**This narrows a LOCKED decision.** 260730-q3f decided: "The build-it TAPPING keyboard keeps
`octaves` pinned at two. `gradeConstructionTap` grades by exact MIDI (it has a distinct
`wrong-octave` outcome), so the octave a note is stacked into must be physically reachable."
The user has now rejected the consequence of that decision twice. The new decision, recorded
in the SUMMARY: **the board fits the phone, and the grader folds to the board.** Physical
reachability is preserved by shrinking the target, not by growing the board.

**Existing coverage that asserts the old behavior:**

- `tests/e2e/tap-targets.spec.ts` lines 265-299, describe
  `piano keyboard row-stacking (octaves=2 pinned)`, enters via
  `openPracticeFamily(page, 'build-it')` and asserts **stacked** at the 375px phone
  viewport. This block breaks and must be re-pointed (Task 2).
- Its doc comment claims "every real construction/voicing drill pins octaves={2}". After
  this change the remaining two-octave pins are `InversionDrill.svelte:292` and
  `ProgressionDrill.svelte:453` (drill stage only). That claim must be corrected.
- `src/lib/components/buildSession.test.ts` lines 273-309 exercise `wrong-octave` by
  clicking the *second* DOM match of a key letter, i.e. the octave-5 duplicate that only a
  two-octave board has. These stay green **only because** jsdom has no `ResizeObserver`, so
  the span stays at its unmeasured default of 2. Preserving that default is a hard
  requirement of Task 2, not an accident.
- No other e2e spec references `.piano-keyboard`.
